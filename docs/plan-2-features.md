# План 2. Базовый функционал мессенджера

Цель: довести возможности до базового уровня лидеров рынка — в выбранном объёме, не шире.
Начинается после [плана 1](plan-1-refactoring.md) и опирается на его результат: доменные
сервисы, `IChatPolicy`, `seq`, outbox, журнал обновлений и `/sync`.

Номера `R*` и `A*` ссылаются на [backend-roadmap.md](backend-roadmap.md).

Оценки — на одного разработчика, грубо. Итого **~13–14 недель**.

До последнего этапа (Ф9) CI нет: тесты гоняются вручную скриптом, деплой ручной —
по правилам [плана 1](plan-1-refactoring.md#правила-выполнения).

### SignalR

SignalR **не блокирует** ни одну функцию из объёма:

- Файлы идут по HTTP (presigned URL), а не через сокет.
- После этапа 2.3 плана 1 команды идут через REST, а сокет только доставляет события.
  Это модель Slack: REST для действий, сокет для событий.
- Гарантии доставки дают журнал и `/sync`, а не транспорт. Поэтому потерянное
  при обрыве событие не проблема: клиент догонит через `/sync`.
- Масштабирование — через Redis backplane, если понадобится.
- Клиентские библиотеки есть для JS, .NET и Java; для Swift есть официальный клиент,
  его зрелость стоит проверить, когда дойдёт до iOS.

Замена транспорта после плана 1 затрагивает только адаптер `IChatEventPublisher` → сокет.
Варианты на будущее: чистый WebSocket со своим протоколом, SSE (события только от
сервера к клиенту; команд по сокету у нас уже нет, так что его хватает), long polling
как запасной вариант. Решение пересмотреть, когда появятся нативные клиенты.

## Решения

**D1. Статусы «отправлено / доставлено / прочитано».**
- «Отправлено» — сообщение получило `seq`.
- «Доставлено» — хотя бы одно устройство получателя подтвердило его через `/sync/ack`
  или получило событие по сокету и подтвердило.
- «Прочитано» — получатель сдвинул `last_read_seq`.
- Хранение — два указателя на участника: `last_delivered_seq` и `last_read_seq`.
  Без записи на каждое сообщение.
- В группе статус считается по участникам: «доставлено/прочитано всеми» или счётчиком.
- События `MessagesDelivered` и `MessagesRead` уходят отправителю и на его устройства.

**D2. Хранение медиа: сейчас сервер, потом, возможно, P2P.**
Чисто P2P-хранение несовместимо с полной историей на новом устройстве. Кроме того:
- для P2P оба устройства должны быть онлайн одновременно;
- в группе файл придётся раздавать каждому;
- за NAT без TURN соединение часто не установится, а TURN — это тот же серверный трафик;
- браузер может вычистить хранилище (IndexedDB) без спроса.

Сейчас делаем серверное хранение (MinIO), но так, чтобы P2P можно было добавить позже:
- сообщение ссылается на `attachment_id`, а не на URL;
- скачивание всегда идёт через API, который решает, откуда взять файл;
- у файла есть `sha256` — пригодится для проверки кусков, полученных от другого
  устройства;
- у файла есть состояние хранения: `stored`, `expired`, в будущем `peer_only`;
- на инстанс есть политика хранения: удалять оригиналы через N дней, оставляя превью
  (по умолчанию выключена).

P2P в будущем — дополнительный способ передачи больших файлов между устройствами,
которые онлайн одновременно (WebRTC DataChannel), а не замена серверу.

**D3. Полная история на новом устройстве.**
Следствие облачной модели. Новое устройство получает всё то же, что видно на старом:
- `/sync/state` — чаты, папки, закрепы, архив, черновики, настройки;
- пагинацию назад до первого сообщения;
- все медиа, пока они хранятся на сервере.

**D4. Черновики.**
Один черновик на пару (пользователь, чат). Сохраняется через REST с задержкой на
стороне клиента. Событие `DraftUpdated` уходит на остальные устройства. Отправка
сообщения очищает черновик.

**D5. Правка и удаление.**
Настройки инстанса, значения по умолчанию:
- правка — автор, в течение 48 часов;
- удаление для всех — автор в течение 48 часов или администратор группы с правом
  удалять чужие сообщения в любое время;
- удаление у себя — всегда.

Удалённое для всех становится «надгробием»: текст и вложения вычищаются, остаётся
`deleted_at`. Сообщение пропадает из поиска и превью.

**D6. Форматирование.**
Текст + `entities` со смещениями:
- типы: жирный, курсив, подчёркнутый, зачёркнутый, код, блок кода с языком, спойлер,
  ссылка с текстом, упоминание (`user_id`);
- до 100 сущностей на сообщение;
- сервер проверяет смещения и схемы ссылок (`http`, `https`, `mailto`) (R31) и что
  упомянутый пользователь состоит в чате.

**D7. Реакции.**
По умолчанию одна реакция на пользователя на сообщение, как в WhatsApp: повторная
заменяет предыдущую. Набор эмодзи задаётся настройкой инстанса. Сводка по реакциям
хранится в сообщении, чтобы не считать её при каждой выдаче.

**D8. Группы.**
- Лимит участников — 500 (настройка инстанса).
- Роли `owner` / `admin` / `member`.
- Права: писать; отправлять медиа; добавлять участников; удалять участников; удалять
  чужие сообщения; менять название и аватар; назначать админов.
- Набор прав на роль + переопределения на участника (A6).
- Журнал действий группы видят админы: добавление и удаление участников, смена ролей
  и прав, переименование, удаление чужих сообщений.
- Добавление в группу проверяет настройку приватности «кто может добавлять».

**D9. Организация чатов.**
- Закрепление — до 10 чатов в основном списке.
- Архив — флаг на участнике. Новое сообщение возвращает чат из архива, если чат
  не заглушён.
- Mute — `muted_until` на участнике (навсегда или до времени). Заглушённый чат
  не шлёт push, но счётчик непрочитанных работает.
- Папки — до 20 на пользователя. Явный список чатов + фильтры по типу (личные,
  группы) и «только непрочитанные». Свой порядок и свои закрепы внутри папки.
- «Пометить непрочитанным» — флаг на участнике; снимается при прочтении.

**D10. Глобальный поиск.**
- Ищет по сообщениям всех чатов, где пользователь сейчас состоит. Исключает удалённые,
  скрытые у себя и очищенные сообщения.
- Результат — сообщение + данные чата для отображения.
- Сортировка по дате, курсорная пагинация.
- Фильтры: чат, отправитель, период, тип (текст или медиа).

**D11. Приватность.**
В продукте нет списка контактов, поэтому «свои» — это участники общих чатов.
- Видимость last seen и online: все / участники общих чатов / никто. Правило
  взаимности как в Telegram: скрыл свой — не видишь чужой.
- Кто может писать в личку: все / участники общих групп / никто. Уже существующий
  личный чат продолжает работать.
- Кто может добавлять в группы: все / участники общих чатов / никто.
- Блокировка: заблокированный не пишет в личку, не добавляет в группы, не видит
  online, last seen и аватар.
- `last_seen_at` сохраняется в БД при отключении последнего соединения — сейчас после
  рестарта сервера его неоткуда взять.

Сделано: все пункты Ф1.1–Ф1.6. Контракт — раздел 12 в
[api-contract-changes.md](api-contract-changes.md). Прогон клиента: новые возможности его
не ломают, но и не видны до доработки фронта (см.
[известные проблемы](manual-checklist.md#известные-проблемы-клиента)). Сводка реакций
пересчитывается под блокировкой строки сообщения: без неё параллельные реакции теряют
голоса — тест с 20 одновременными реакциями без блокировки падает.

Уточнения к решениям:
- **Удалённое для всех не показывается в истории**, как в Telegram: страницы, поиск и
  превью его пропускают, клиенту приходит `MessageDeleted`. Строка-«надгробие» остаётся в
  БД, чтобы не рвать `seq`, ответы и указатели прочтения. Текущий клиент ничего не знает о
  новых событиях, но после перезагрузки увидит правильную историю.
- **Настройки инстанса пока в конфигурации** (`Messages:EditWindowHours` и т. п.), а не в
  таблице `instance_settings`: менять их без рестарта пока некому. Таблица появится вместе
  с интерфейсом администратора.
- **Счётчик упоминаний считается запросом** по таблице `message_mentions` (как счётчик
  непрочитанных), а не хранится в `chat_members.mention_count`: хранимый счётчик пришлось

Уточнения к решениям:
- **Статус в группе — «хотя бы один участник»**, как в Telegram, а не «все». Статус «всеми» в
  группе на сотни человек почти не достигается, и клиенту для него нужны указатели каждого
  участника. «Хотя бы один» монотонен: клиенту хватает одного числа на чат — максимума по
  чужим указателям. Список «кто прочитал» — отдельной ручкой, если понадобится.
- **«Доставлено» — только по `/sync/ack`.** Отправка в сокет не значит, что клиент событие
  обработал. Текущий клиент ack не шлёт: у него сообщения переходят из «отправлено» сразу в
  «прочитано».
- **События статусов — только при смене статуса.** Иначе в группе каждое подтверждение каждого
  участника расходилось бы всем: 500 участников × 500 подтверждений на сообщение.

Уточнения к решениям:
- **Системные сообщения** — `type: "system"` с `action` (что произошло) и запасным текстом
  по-русски: текущий клиент покажет его как обычное сообщение. Их нельзя редактировать,
  пересылать и отвечать на них; удалить у всех может только админ с правом удалять чужие.
- **Исключённый или вышедший теряет чат** вместе с историей — строка участника удаляется.
  Вернувшийся видит всю историю, но непрочитанное считается с момента возвращения.
- **Права участников** — только `sendMessages`, `sendMedia`, `addMembers`, `changeInfo`;
  права админа (`removeMembers`, `deleteMessages`, `addAdmins`) участнику не выдаются —
  для этого его назначают админом.
- **Порядок в списке чатов** — по `chats.last_activity_at`, общему для всех участников.
  Удаление последнего сообщения чат вниз не сдвигает, как в Telegram. `last_message_id` в
  `chats` не заводим: превью у каждого своё (скрытые у себя сообщения), его по-прежнему
  выбирает запрос — но только для страницы, а не для всего списка.
- **Изменения состава и ролей группы идут по одному** — под блокировкой строки чата. Без неё
  две одновременные передачи владения давали 500 на уникальном индексе владельца, а два
  одновременных добавления обходили лимит участников; оба случая закрыты тестами.
- **Исключённый перестаёт получать события сразу**: его соединения выводятся из SignalR-группы
  чата той же отправкой из outbox, что и `MemberRemoved`, — порядок событий сохраняется. Тест
  без этого шага падает: исключённому приходит следующее сообщение группы.
- **Права по умолчанию и переопределения** — «указанное побеждает»: переопределение участника
  может как ограничить, так и разрешить больше, чем по умолчанию в группе (например, дать
  писать одному участнику в группе «только для чтения»).

Уточнения к решениям:
- **Хранилище — SeaweedFS, а не MinIO.** Сообщество MinIO перестало получать готовые сборки
  и образы, репозиторий архивирован (2025–2026). SeaweedFS — Apache 2.0, S3 API, один
  контейнер (`weed mini`), ~60 МБ памяти. Код работает с любым S3 (AWS SDK), так что
  хранилище заменяемо настройкой `Storage:*`.
- **Хранилище отдаётся с адреса сайта** (`/media/…` через Caddy): не нужен второй домен и
  сертификат, CSP сайта не расширяется. От исполнения загруженного на сайте (R32) защищает
  другое: сервер сам выбирает тип и `Content-Disposition` при подписи ссылки (не то, что
  заявил загрузивший), а Caddy добавляет к файлам `nosniff` и `CSP: sandbox`.
- **Тип файла — по содержимому.** Заявленный клиентом тип идёт только в показ. Превью
  перекодируется из пикселей, поэтому в него не попадают метаданные (EXIF с геометкой) и
  приклеенное к файлу; сам оригинал отдаётся как есть.
- **Альбом — одно сообщение с несколькими файлами**, а не группа сообщений, как в Telegram:
  подпись одна, правка и удаление — целиком, счётчик непрочитанных считает альбом за одно.
- **Доступ к файлу идёт за сообщением:** его видят участники чатов, куда он отправлен, и
  загрузивший. Удаление у всех забирает доступ; файл, на который больше ничего не ссылается,
  удаляется через сутки. Аватар — только из своих загрузок, видят его все вошедшие (группы —
  участники).
- **Ссылки на скачивание меняются при каждом запросе** (подпись со временем), поэтому браузер
  не кэширует картинку между запросами ссылок. Стабильные ссылки (подпись с округлённым
  временем) — если это станет заметно.

- **«Контакты» — те, с кем есть общий чат**: списка контактов в продукте нет. Для присутствия

- **Скрытое присутствие — это «не в сети» без времени**, а не 404: собеседник остаётся

- **Блокировка не сообщается заблокированному**: он получает тот же `PRIVACY_RESTRICTED`, что и

- **Добавление в группу — всё или ничего**: если кого-то добавить нельзя, не добавляется никто, а
  ответ перечисляет их в `userIds`. Добавить часть и молча пропустить остальных — хуже: создатель
  не узнает, кого нет.
- **Смена пароля закрывает остальные входы сразу** — refresh-токены и соединения с хабом;
  access-токены живут до истечения (минуты), как и при выходе.
- **Найдено по ходу:** соединение, оборвавшееся во время подключения к хабу, оставляло
  пользователя «в сети» до рестарта — SignalR не вызывает `OnDisconnectedAsync`, если упал
  `OnConnectedAsync`. Тест с быстрыми подключениями и отключениями падал; исправлено в Ф5.1.

Уточнения к решениям:
- **Устройство — это вход**, а не отдельная регистрация от клиента: у каждого входа уже есть
  `sid` в токене, отзыв и разрыв соединений. Строка `devices` появляется в одном запросе с первой
  сессией входа, поэтому не бывает входа без устройства и наоборот.
- **WebPush через библиотеку** Lib.Net.Http.WebPush (на .NET без BouncyCastle), а не своё
  шифрование. Сквозной тест расшифровывает то, что уходит в push-сервис, кодом, написанным по
  RFC 8291 независимо от библиотеки, и проверяет подпись VAPID.
- **Адрес подписки — только известных push-сервисов** (`Push:AllowedHosts`). Адрес присылает
  клиент, и без списка сервер слал бы POST куда скажут, в том числе на внутренние адреса (SSRF).
- **Подписка переходит к последнему вошедшему в браузере.** Браузер отдаёт одну подписку на
  сайт: если Алиса вышла, а Боб вошёл и подписался, уведомления Алисы не должны показываться Бобу.
- **Кому слать, решается в момент отправки**, а не при записи события: получатели — подписанные
  устройства участников, кроме отправителя, заглушивших чат, заблокировавших отправителя и тех,
  у кого открыто соединение (им сообщение приходит по хабу). «Открыто соединение» — на уровне
  пользователя, как в плане: открытая вкладка на ноутбуке гасит push на телефон.
- **Очередь отправки — в памяти.** Push-сервисы медленнее хаба и бывают недоступны — они не
  должны задерживать события в outbox. Уведомление, потерянное при перезапуске, не стоит
  отдельной таблицы: сообщение есть в журнале `/sync`. При нескольких инстансах API «открыто
  соединение» знает только свой инстанс — понадобится общий backplane, как и для хаба.
- **Упоминания в заглушённом чате не уведомляют** (D9: заглушённый чат не шлёт push); в
  Telegram по умолчанию уведомляют — можно добавить настройкой, когда появится клиент.

Сравниваются чаты, сообщения, правки, удаления, реакции, статусы, прочтение, черновики, закрепы, архив, mute, папки, приватность, блокировки и профиль; потом Б догоняет журналом и снова сверяется. | Ф8.2 | **Документация и проверка.** Контракт, чек-лист, прогон текущего клиента за Ф7 и Ф8, сквозные тесты на стеке. |

Порядок важен:
- Ф1 → Ф2: статусы и счётчики зависят от новой модели сообщения.
- Ф3 без аватаров → Ф4 добавляет аватары групп и пользователей.
- Ф5 и Ф6 независимы друг от друга.
- Ф7 (push) — после Ф6: нужен mute.
- Ф8 — после всех функциональных этапов, Ф9 — последним.

## Контракты

Все новые события и эндпоинты — только добавления. Каждое изменение вносится в
[api-contract-changes.md](api-contract-changes.md) по ходу этапа, а не в конце. Фронт
подключает новые функции в своём темпе. Старые события продолжают приходить, пока
фронт не перейдёт на `/sync` и новые типы событий.

При доработке фронта — починить известные проблемы текущего клиента из
[чек-листа ручной проверки](manual-checklist.md#известные-проблемы-клиента):
переподключение хаба с истёкшим access-токеном и отсутствие повторных попыток после
отказа (обе оставляют пользователя без событий до F5).

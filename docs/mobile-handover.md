# Передача мобильному клиенту: что изменилось с 31 августа

Для разработчика Android-клиента, который последний раз синхронизировался с бэкендом около
2026-08-31 (разделы 1–8 [api-contract-changes.md](api-contract-changes.md)). Всё ниже добавлено
2026-09-29 … 2026-10-02 (планы 1–6). Ссылки «§N» — разделы
[api-contract-changes.md](api-contract-changes.md); подробности, тела запросов и коды ошибок — там.

**Про push на Android.** Нативного FCM или APNs на сервере нет. `fcm.googleapis.com` в
`Push:AllowedHosts` — это адрес WebPush-подписки Chrome, а не FCM-токен приложения:
`PUT /api/push/subscription` принимает только `PushSubscription.toJSON()` браузера (endpoint +
`p256dh` + `auth`), полезная нагрузка зашифрована по WebPush. Для нативного приложения push
сейчас нет — нужна отдельная доработка сервера. До неё — догон по `/api/sync` при открытии.

**Голосовые и видео** — это файлы-вложения (`kind: voice` / `video`), звонков нет.

## 2. Что изменилось и ломает клиент с 31 августа

Формально почти всё аддитивно, но клиент, написанный по §1–8, столкнётся со следующим.

**Авторизация и сессии**

- Время жизни access-токена — настройка: 30 мин по умолчанию, в прод-примере 60 мин
  (`JWT_EXPIRY_MINUTES`). Брать `expiresAt` из ответа, не зашивать.
- Access-токен закрытого входа (logout, выход устройства, logout-all, смена пароля) перестаёт
  работать сразу (кеш на сервере до 15 с): `401 TOKEN_MISSING_OR_EXPIRED`, затем refresh →
  `401 SESSION_REVOKED` → экран входа. После `logout-all` не работает и токен самого запроса. §23.6
- Refresh, пришедший одновременно с выходом, получает `401 SESSION_REVOKED`, а не новую пару. §23.2
- `POST /api/auth/logout` теперь закрывает и вход (`sid`) access-токена запроса, даже если
  `refreshToken` в теле уже устарел. §22.1
- Смена пароля: неверный текущий — `400 WRONG_PASSWORD`, не `401` (не путать с истёкшим
  токеном). §16.4
- Регистрация может быть закрыта (`403 REGISTRATION_CLOSED`) или требовать `inviteCode`
  (`403 INVITE_INVALID`); режим — `GET /api/auth/registration` без входа. §23.12
- `GET /api/users/GetUserId/{username}` — только по логину, по email теперь `404`. §9.8

**Хаб SignalR**

- Хаб — канал событий; команды — через REST. `SendMessage`/`Typing` в хабе остались, но не
  принимают `clientMessageId`, ответы, разметку и файлы. §10.1
- Соединение живёт, пока жив вход, а не access-токен; переподключаться всё равно со свежим
  токеном. Старый токен закрытого входа — соединение обрывается сразу после подключения. §9.1, §11
- Ошибки методов хаба — `HubException`, код — слово после `HubException: `
  (`/HubException: ([A-Z_]+):/`). `JoinChat` чужого чата — `NOT_A_MEMBER`. §9.2, §9.3
- `JoinChat`, `SendMessage`, `Typing` — 20 вызовов за 10 с на соединение (`RATE_LIMITED`);
  не больше 20 соединений хаба на пользователя, лишнее закрывается сразу. §23.7
- События `MessageCreated`, `ChatListUpdated`, `ChatCreated` и все журналируемые идут через
  outbox: в редком случае приходят **дважды** — дедуплицировать по `id` сообщения / `chatId`. §10.4

**Сообщения и модель данных**

- Все даты — UTC с `Z`. §10.2
- `MessageDto`: новые поля `seq`, `clientMessageId`, `type` (`text`, `media`, `system`;
  незнакомый — заглушкой), `editedAt`, `replyTo`, `forwardFrom`, `entities`, `reactions`,
  `myReaction`, `status`, `attachments`, `action`. В `seq` бывают пропуски (удалённые у всех). §10.3, §12, §13.1, §14.1, §15.2
- `isRead` поменял смысл: у своего — `status == read`, у чужого — прочитал ли его я. §13.1
- Сообщение с файлами может иметь пустой `text`. Системные сообщения (`type: system`) приходят в
  историю; подпись строить из `action`, `text` — запасной вариант. §14.1, §15.2
- Тип чата `saved`; у группы — `role`, `myRole`, `myPermissions`. §12.5, §14.2
- `unreadCount` не считает свои сообщения; указатель прочтения двигается только вперёд. §9.6
- `GET /api/chats` возвращает и архивные чаты (`archived: true`), закреплённые — сверху. §17.1
- `lastActivityAt` — последняя активность чата для всех, а не последнее видимое мне сообщение. §14.6
- Превью без разметки (`lastMessage.text`, `replyTo.text`, `ChatListUpdated`, push) — спойлеры
  заменены на `▒▒▒▒`. §22.3
- `lastMessage` в карточке — превью без разметки, реакций, ответа; историю по нему не строить. §19.2
- Все поля ответа присутствуют всегда (в т.ч. `null`), кроме помеченных `x-omitted-when-null`
  (`url`, `userId`, `language` у entities и др.). §20.1
- `nextCursor = null`, когда `hasMore = false`; формат курсора другой — он непрозрачная строка;
  битый — `400 INVALID_CURSOR`. §9.7, §10.3
- Статус пользователя: `lastSeenAt`; скрывший присутствие — `isOnline: false, lastSeenAt: null`. §16.1

**Новые отказы на старых ручках**

- `POST /api/chats/private/{userId}`: первый вызов `201`, повтор `200`; `403 PRIVACY_RESTRICTED`
  по настройкам собеседника; `404 USER_NOT_FOUND`. §9.4, §16.2
- Отправка в личке с блокировкой: `403 USER_BLOCKED` (я заблокировал) или
  `403 PRIVACY_RESTRICTED` (меня). В группе без права — `403 PERMISSION_DENIED`. §16.3, §14.2
- Исключение из группы: `MemberRemoved` со своим `userId` → убрать чат; дальше `NOT_A_MEMBER`. §14.3

**Синхронизация**

- После любого переподключения — `GET /api/sync?since={pts}` до `hasMore: false`.
  `snapshotRequired: true` — заново `GET /api/sync/state`. Теперь это бывает и при отставании
  больше чем на 1000 записей, и при дыре в журнале. §10.5, §23.10
- Снимок `GET /api/sync/state` несёт всё состояние: `chats` (с архивом, черновиками, закрепами),
  `folders`, `privacy`, `blockedUserIds`, `me`. §19.1

**Ошибки и лимиты**

- Все ошибки REST — `application/problem+json` с `errorCode` и `traceId`; ветвиться по `errorCode`.
  Полный список — [справочник кодов ошибок](api-contract-changes.md#справочник-кодов-ошибок).
- Лимиты: 300 запросов/мин на пользователя, 100/мин на анонимный IP, вход/регистрация/смена
  пароля — 5/мин с IP; команды (отправка, правка, удаление, реакции и т. п.) — 20 за 10 с на
  пользователя; «печатает» и черновики — свои 20 за 10 с. Превышение — `429 RATE_LIMITED` с
  `Retry-After`. §10.1, §21.1, [capacity-and-limits.md](capacity-and-limits.md)
- Тело больше лимита ручки (64 КБ у отправки, правки, черновика; 1 МБ на прокси) —
  `413 REQUEST_TOO_LARGE`; оборванное тело — `400 BAD_REQUEST`. §21.2

**Загрузка файлов**

- `PUT {uploadUrl}`: `Content-Type` ровно `contentType` из ответа и тело ровно `size` байт из
  запроса (`Content-Length` входит в подпись, иначе `403` от хранилища). Кадр видео — до 2 МБ. §15.1, §23.3
- PNG/GIF больше `media.maxPngGifPhotoPixels` (12 Мп) как `photo` отклоняются
  `400 INVALID_MEDIA` — отправлять их с `kind: file`. §23.1

`clientMessageId` **не обязателен** (без него отправка работает), но без него повтор после
обрыва сети создаст дубль — генерировать UUID на каждое сообщение. §10.3

## 3. Порядок работы клиента

1. **Вход.** `POST /api/auth/login` `{ usernameOrEmail, password }` → `token`, `expiresAt`,
   `refreshToken`, `refreshTokenExpiresAt`. Хранить оба токена; refresh-токен меняется при
   каждом `POST /api/auth/refresh` — всегда сохранять новый.
2. **На `401 TOKEN_MISSING_OR_EXPIRED`** — `POST /api/auth/refresh` `{ refreshToken }` и повтор
   запроса один раз. Любой `401` от refresh — экран входа. Параллельные refresh безопасны (окно 30 с). §8
3. **Конфигурация.** `GET /api/config` — лимиты, набор реакций, `media.enabled`, `push.enabled`.
4. **Снимок.** `GET /api/sync/state` → запомнить `pts`, построить список чатов, папки, профиль.
5. **Хаб.** `wss://{host}/hubs/chat?access_token={token}` (SignalR-клиент: `accessTokenFactory`
   с актуальным токеном). Перед переподключением — обновить токен. Подписаться на события
   (список — в `/signalr-docs` или `components.schemas` снимка OpenAPI).
6. **После каждого (пере)подключения** — догон: `GET /api/sync?since={pts}&limit=100`, применить
   `updates` по порядку (`type` = имя события хаба, `payload` = его тело), сохранить `pts`,
   повторять, пока `hasMore`. `snapshotRequired` → шаг 4. Обработчики событий хаба и журнала —
   общие и идемпотентные.
7. **Открытый чат.** `JoinChat(chatId)` — `MessageCreated` живьём приходит только соединениям,
   вошедшим в чат; при уходе — `LeaveChat`. История — `GET /api/chats/{id}/messages/cursor`.
   Прочтение — `POST /api/chats/{id}/read` `{ lastMessageId }`.
8. **Остальные чаты.** `ChatListUpdated(chatId, preview)` приходит на все соединения: поднять
   строку по превью (`seq`, `type`, обрезанный текст), счётчики и полное сообщение — из догона
   по журналу (так делает веб-клиент). §22.2
9. **Отправка.** UUID → `clientMessageId`; показать «отправляется»; `POST
   /api/chats/{id}/messages` `{ text, clientMessageId, entities?, replyToMessageId?, attachmentIds? }`.
   При обрыве повторять с тем же id (повтор — `200` с тем же сообщением). Своё сообщение из
   `MessageCreated` сопоставлять по `clientMessageId`.
10. **Доставка.** `POST /api/sync/ack` `{ pts }` раз в несколько секунд и при уходе в фон —
    от этого зависит статус `delivered` у собеседников. §13.1
11. **Файл.** `POST /api/media/uploads` `{ kind, fileName, mimeType, size, … }` →
    `PUT uploadUrl` (точный `Content-Type` и размер) → `POST /api/media/uploads/{id}/complete` →
    `attachmentId` в `attachmentIds` сообщения. Показ — `POST /api/media/links`
    `{ attachmentIds }` (ссылки живут 60 мин). §15.1
12. **Выход.** `POST /api/auth/logout` с Bearer и `{ refreshToken }`, затем стереть локальное.

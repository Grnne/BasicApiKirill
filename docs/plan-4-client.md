# План 4: веб-клиент догоняет бэкенд

Цель: `BasicWebClient` умеет всё, что умеет бэкенд после планов 1–3, и не теряет события.
После плана из [чек-листа](manual-checklist.md) уходят отметки «API» и раздел «Известные
проблемы клиента».

## Исходное состояние

**Что умеет клиент.** Около 2 тыс. строк: Vue 3, Pinia, SignalR, без UI-библиотек.
- Вход, регистрация, refresh-токен.
- Список чатов, личный чат по поиску людей, поиск чатов.
- Лента с подгрузкой вверх, отправка текста через хаб.
- «Печатает» и онлайн.
- Тестов нет. В `scripts/test.ps1` и CI клиент не проверяется: его собирает только
  `docker build`.

**Чего не хватает.**

| Область | Не поддержано |
|---|---|
| Доставка событий | `/api/sync` и `pts` не используются. Событие, пропущенное при обрыве, теряется до F5. Хаб сдаётся через ~47 с. При реконнекте с истёкшим токеном — 401 |
| События хаба | Слушаются 5 из 23. Нет `MessageUpdated`, `MessageDeleted`, `ReactionsChanged`, `MessagesDelivered`, `MessagesRead`, `ReadStateChanged`, `DraftUpdated`, `ChatUpdated`, `ChatDeleted`, `MemberAdded/Removed/Updated`, `UserUpdated`, `PrivacyUpdated`, `BlockListChanged`, `PinnedChatsChanged`, `ChatStateChanged`, `FoldersChanged` |
| Отправка | Через хаб: без `clientMessageId`, без повтора, без «отправляется». На любую ошибку — «проверь связь» |
| Сообщения | Правка, удаление, ответ, пересылка, разметка и упоминания, реакции, системные сообщения |
| Статусы | Галочки «отправлено / доставлено / прочитано». Метка «непрочитано». Черновики. Счётчик упоминаний. Прочтение сообщения, пришедшего в открытый чат |
| Список чатов | «Избранное», закреп и его порядок, архив, mute, папки, страницы |
| Поиск | По сообщениям в чате, глобальный, переход к дате и к найденному сообщению |
| Медиа | Загрузка, вложения и альбомы, превью, галерея чата, аватары |
| Группы | Создание, участники, роли и права, переименование, аватар, выход, удаление, журнал действий |
| Профиль | Имя, аватар, пароль, приватность, блокировки, устройства, выход везде |
| Push | Service worker, подписка, переход в чат по уведомлению |

## Правила плана

- Действуют общие правила [CLAUDE.md](../CLAUDE.md). Правило «фронт не трогаем» снимается в К0
  и заменяется правилами для клиента.
- Перед коммитом `scripts/test.ps1`. С К0 он же проверяет клиент: `npm ci`, `vue-tsc`,
  `vitest`. Строка-итог — в сообщение коммита.
- **Тесты клиента.**
  - Логика (применение событий, статусы, очередь отправки, разбор разметки) — чистые функции
    и сторы, покрываются Vitest.
  - Компоненты, где есть риск безопасности или сложный вывод (разметка, ссылки, вложения), —
    `@vue/test-utils` + `happy-dom`.
  - Баг клиента сначала воспроизводится таким тестом.
- **Контракт.** Типы REST генерируются из снимка OpenAPI
  (`BasicApi.IntegrationTests/Snapshots/openapi.json`) в `src/shared/api/schema.d.ts`. Тест
  сверяет, что сгенерированный файл свежий. Так расхождение клиента с бэкендом ловится сборкой,
  а не чек-листом. Полезные нагрузки событий хаба, которых нет в OpenAPI, описываются руками
  в одном файле рядом.
- **Бэкенд в этом плане меняется, только если клиенту чего-то не хватает.** Изменения
  аддитивные, отдельным коммитом, с тестом и записью в
  [api-contract-changes.md](api-contract-changes.md). Уже известно одно такое изменение — К0.3.
- **Безопасность клиента не ослабляется.**
  - Без `v-html`: разметка собирается из VNode.
  - Ссылки — только `http`/`https`/`mailto`, с проверкой и на клиенте.
  - CSP в `index.html` расширяется ровно на то, что нужно (воркер push, медиа в деве).
- Новые runtime-зависимости — только при явной нужде. Dev-зависимости: `vitest`,
  `@vue/test-utils`, `happy-dom`, `openapi-typescript`.
- Каждый этап заканчивается проверкой в двух окнах на локальном стеке: встроенный браузер,
  два пользователя. Перед подъёмом стека — проверка свободной памяти.

## Устройство клиента после плана

Раскладка та же (`app / pages / features / entities / shared`, импорт только вниз). Меняется
ядро.

```
shared/api/schema.d.ts      сгенерированные типы REST
shared/api/events.ts        типы событий хаба и журнала (то, чего нет в OpenAPI)
entities/sync/              движок синхронизации: снимок, pts, догон, ack
entities/chat|message|user  состояние и чистые функции применения событий (reducers)
features/*                  действия пользователя: api + model + ui
```

**Синхронизация — главное изменение.** Сейчас сторы фич подписаны на хаб напрямую. Будет так:
1. При старте — `GET /api/sync/state`: чаты, папки, приватность, блокировки, `me`, `pts`.
2. Живые события хаба и записи журнала `GET /api/sync?since=` проходят **через одни и те же
   функции применения**. Применение идемпотентно, потому что событие может прийти дважды
   (хаб + журнал, повтор outbox):
   - сообщения узнаются по `id`;
   - счётчики двигаются только по `seq`;
   - статусы и указатели только растут.
3. Живые события не несут `pts`. Поэтому после пачки событий (с паузой ~1 с), после
   реконнекта и при возврате вкладки клиент делает `GET /api/sync` и двигает `pts`. Затем
   `POST /api/sync/ack` — отсюда статус «доставлено».
4. `snapshotRequired` — заново шаг 1.

Ленту открытого чата по-прежнему ведёт стор сообщений. Он получает те же применённые события.

## Этапы

Один пункт — один коммит. Порядок важен: К1 — фундамент для всего остального.

### К0. Инфраструктура

| # | Что |
|---|---|
| К0.1 | `CLAUDE.md` и `architecture.md`: правила для клиента вместо «не трогаем». Vitest + happy-dom + test-utils. `scripts/test.ps1` (и CI): `npm ci`, `npm run check`, `npm test`, с ключом `-SkipClient`. В CI — `setup-node` |
| К0.2 | Генерация типов из снимка OpenAPI (`npm run gen:api`) и тест свежести. Типы `entities` переводятся на сгенерированные. Попутно ловим, где клиент уже расходится с контрактом |
| К0.3 | **Бэкенд:** `GET /api/config` — набор реакций, лимиты (длина сообщения, размер файла, файлов в альбоме, участников группы), включён ли push и медиа. Сейчас реакции задаются настройкой сервера, клиенту их не узнать. Аддитивно, с интеграционным тестом, снимок OpenAPI обновляется |
| К0.4 | Дев-окружение для медиа: прокси `/media` в Vite и `Storage__PublicUrl` для локального запуска, чтобы файлы шли с того же origin, что в проде за Caddy. README клиента |
| К0.5 | Комментарии клиента — на английский и только о важном, как в С5 плана 3 (сейчас там подробные русские комментарии) |

### К1. Ядро: синхронизация, соединение, отправка

| # | Что | Закрывает |
|---|---|---|
| К1.1 | Движок синхронизации (снимок, `pts`, догон, ack), единый диспетчер событий, перевод списка чатов и ленты на него. Тесты: повтор события, пропуск при обрыве, `snapshotRequired`, `hasMore` | потерю событий при обрыве |
| К1.2 | Соединение. Токен в `accessTokenFactory` обновляется и когда он истёк, а не только когда его нет (по `exp`). После исчерпания авто-реконнекта — свой цикл с нарастающей паузой; повтор при `online` и возврате вкладки. «Нет связи» с кнопкой «Повторить» | обе проблемы реконнекта из чек-листа |
| К1.3 | Отправка через REST с `clientMessageId`. Временная копия «отправляется» заменяется настоящей по `clientMessageId`. Повтор при сетевой ошибке, «не отправлено — повторить». Ошибки по `errorCode` (`PRIVACY_RESTRICTED`, `RATE_LIMITED` с `Retry-After`, …). «Печатает» — через REST | неверную подсказку «проверь связь» |
| К1.4 | Прочтение. Сообщение, пришедшее в открытый и видимый чат, отмечается прочитанным (с паузой). `ReadStateChanged` обновляет счётчики с других устройств. Ошибки входа — по `errorCode` и по-русски (`USERNAME_TAKEN`) | непрочитанное после F5 и английскую ошибку |

### К2. Сообщения

| # | Что |
|---|---|
| К2.1 | Полный `MessageDto` в ленте. Разметка и упоминания из `entities` — компонент на VNode, тесты на `javascript:`-ссылки и смещения с суррогатными парами. Системные сообщения (`action`) — строкой по центру. «изменено» |
| К2.2 | Контекстное меню сообщения. Правка своего (`PATCH`), удаление «у меня / у всех», надгробие. `MessageUpdated`, `MessageDeleted`, пересчёт превью в списке |
| К2.3 | Ответ: цитата в композере и в пузыре, переход к исходному. Пересылка: выбор чата, подпись «Переслано от …». Выделение нескольких сообщений для пересылки |
| К2.4 | Реакции: набор из `/api/config`, счётчики под сообщением, своя подсвечена. `ReactionsChanged` |
| К2.5 | Разметка при наборе: жирный, курсив, код, ссылка (горячие клавиши и выделение). Упоминание `@` с подсказкой участников группы. Композер отдаёт `text + entities` |

### К3. Статусы и черновики

| # | Что |
|---|---|
| К3.1 | Галочки своих сообщений по `outboxDeliveredSeq` / `outboxReadSeq`. `MessagesDelivered`, `MessagesRead`. В «Избранном» статусов нет |
| К3.2 | Метка «непрочитано» (меню чата), точка в списке, снятие при открытии. Счётчик упоминаний `@` |
| К3.3 | Черновики. Сохранение с паузой 1–2 с, восстановление при открытии чата, «Черновик: …» в списке. `DraftUpdated` без перетирания набираемого текста (по `updatedAt`) |

### К4. Список чатов: организация

| # | Что |
|---|---|
| К4.1 | Порядок как у сервера: закреплённые по `pinnedPosition` сверху, дальше по активности. Закрепить / открепить, перетаскивание закреплённых (`PUT /pinned`). `PinnedChatsChanged` |
| К4.2 | Архив отдельной строкой «Архив» со своим списком. В архив / из архива. Mute со сроком, иконка, без счётчика в общем. `ChatStateChanged` |
| К4.3 | «Избранное»: тип `saved`, свой заголовок и иконка, пункт «Избранное» в меню (`POST /chats/saved`) |
| К4.4 | Папки: вкладки над списком, создание и правка (название, чаты, правила), удаление, порядок. `FoldersChanged` |
| К4.5 | ~~Список страницами (`GET /chats/page`)~~ — **не нужен.** Клиент получает все чаты в снимке `/sync/state` (он нужен для синхронизации), поэтому страницы не уменьшают ни трафик, ни память. Если список в тысячи чатов станет тормозить при отрисовке — виртуальная прокрутка, а не страницы |

## Риски

- **Объём.** Клиент вырастет в 4–5 раз. Этапы К2–К9 независимы друг от друга после К1, и их
  можно переставлять.
- **Двойное применение событий.** Главный источник багов синхронизации. Поэтому применение —
  чистые функции с тестами на повтор и порядок.
- **Push** работает только по HTTPS (на `localhost` — тоже). Проверяется на локальном прод-стеке
  с VAPID-ключами, как в плане 2.

# Пропускная способность и лимиты

Что сервер выдерживает при текущих настройках, что упирается первым и что с этим
делать.

> **Цифры измерены** нагрузочными прогонами (методика, таблицы и как повторить —
> [load-testing.md](load-testing.md)). Генератор нагрузки стоял на той же машине, так что на
> отдельном сервере цифры будут не хуже.

---

## Малый сервер — настройки по умолчанию

`docker-compose.prod.yml` по умолчанию рассчитан на маленький сервер: 2 ГБ памяти (часть занята
системой и другими службами), одно ядро, **до ~100 клиентов онлайн**. Лимиты памяти в сумме — 1 ГБ:

| Контейнер | Лимит | Что ещё | Пик при 100 клиентах |
|---|---|---|---|
| Postgres | 320 МБ (`POSTGRES_MEMORY`) | `shared_buffers=64MB`, `max_connections=30`, shm 64 МБ | 88 МБ |
| API | 256 МБ (`API_MEMORY`) | пул Npgsql 10 (`DB_POOL_SIZE`), workstation GC, `GCConserveMemory` | 88 МБ |
| SeaweedFS | 256 МБ (`STORAGE_MEMORY`) | | 128 МБ |
| Caddy | 192 МБ (`CADDY_MEMORY`) | ~230 КБ на соединение | 46 МБ |
| **Всего** | **1 ГБ** | | **~350 МБ** |

Замер 2026-10-01: все четыре контейнера на одном общем ядре, 100 подключённых из 200
пользователей, 5 отправок и 2 открытия списка в секунду — с запасом против живой команды. Отправка
p95 21 мс, доставка p95 23 мс, ни одного потерянного события. После рестарта API все 100 клиентов
вернулись за 3,8 с; списки чатов в этой волне — p50 0,8 с, 15 ответов 502 от Caddy (API ещё не
поднялся) — клиент их повторяет. В покое стек занимает ~190 МБ.

Запас по памяти — на рестарт, загрузку файлов и автовакуум. На сервере стоит держать swap хотя бы
на 1 ГБ: при нехватке памяти ядро без него убьёт один из процессов, и это может оказаться Postgres.

**Больше клиентов** — поднять переменные в `.env.prod` (`.env.prod.example`, раздел «Memory»).
Профиль, на котором сняты цифры ниже, для ~2000 клиентов: Postgres 768 МБ и
`shared_buffers`/`max_connections` по умолчанию (128 МБ / 100), API 512 МБ и пул 30, Caddy 512 МБ, у
каждого контейнера своё ядро.

## Коротко (профиль на ~2000 клиентов)

- **2000 одновременно подключённых** при 80 отправках и 40 открытиях списка чатов в
  секунду: API занят на половину ядра, Postgres — на 40%, p95 отправки — 44 мс,
  ни одного потерянного события. Запас по штатной нагрузке есть.
- **Первым упирается память Caddy**: ~220–250 КБ на открытый WebSocket. С лимитом
  512 МБ — примерно до 2000–2400 клиентов (раньше при 128 МБ — около 1000).
- **Самое слабое место — рестарт API** (деплой): 1000 клиентов возвращаются за ~11 с,
  2000 — до полутора минут, а их списки чатов в пике идут по 6–13 с. См.
  [«Массовый реконнект»](#массовый-реконнект).

Число **зарегистрированных** пользователей ограничением не является — это строки в БД.

## Что во что упирается

Измерено; «потолок» — оценка по росту ресурса с числом клиентов.

| Ресурс | Что расходует | Сколько | Потолок |
|---|---|---|---|
| Caddy, память 512 МБ | Открытые WebSocket (буферы TLS и прокси) | ~220–250 КБ на соединение: 250 МБ на 1000, 425 МБ на 2000 | **~2000–2400 клиентов**, дальше OOM-kill и падение всего входа |
| API, память 512 МБ | Соединения хаба, presence | 93 МБ на 250, 148 МБ на 1000, 159 МБ на 2000 | тысячи клиентов, не первое, что кончится |
| API, 1 CPU | Отправки, списки чатов, подключения | 52% при 2000 клиентах и 80 отпр/с; 99% в волне подключений после рестарта | штатно — с запасом; в рестарт — упор |
| Postgres, 1 CPU | Список чатов — самый частый и тяжёлый запрос | 40% при 80 отпр/с + 40 спис/с; 99% в волне списков после рестарта | штатно — с запасом; в рестарт — упор |
| Пул Npgsql 30 / `pids: 100` у Postgres | Одновременные запросы к БД | в волне реконнекта пул занят целиком, запросы ждут в очереди — ошибок нет | см. ниже |
| BCrypt при логине, 1 CPU | ~100 мс на хеш | не мерилось (логин вне прогона) | ~10 логинов/с |
| Rate limit | 300 запросов/мин на пользователя, 100/мин на анонимный IP, auth — 5/мин на IP | — | клиенты за общим NAT при логине |

## Пул Npgsql и `pids: 100`

Пул переиспользует физические соединения **во времени, а не между одновременными
запросами**: если десять запросов держат по соединению, одиннадцатому открывается
новое — до `Maximum Pool Size`. У Postgres в контейнере `pids: 100`: процесс на
соединение плюс ~8 служебных, то есть ~90 клиентских соединений.

Поэтому пул ограничен **30** (строка подключения в `docker-compose.prod.yml`): под
пиком запросы ждут в очереди пула (до `Timeout=15`), а не получают отказ сервера на
сотом соединении. На одном ядре Postgres 30 соединений с очередью ещё и быстрее, чем
сто конкурирующих. Прогон это подтвердил: в волне из ~1800 списков чатов после
рестарта Postgres был загружен на 99%, списки шли по 6–13 с, но ни одной ошибки.
pgbouncer на таких объёмах не нужен.

## Список чатов

Один запрос на весь список (`GetUserChatsBatchedAsync` → `SearchChatsBatchedAsync` в
`ChatRepository.cs`), не N+1. Внутри — коррелированный подзапрос на непрочитанные
(по индексу `(chat_id, seq)`) и два LATERAL-джойна (собеседник, последнее сообщение),
по строке на чат. Фильтр участника идёт по индексу `ix_chat_members_user_id`; без него это был линейный просмотр всей `chat_members` на каждое
подключение к хабу и каждый запрос статусов.

Замер: при 20 чатах у пользователя и 40 000 участников в базе список отдаётся за
4–10 мс (p50) и 7–35 мс (p95) под штатной нагрузкой. Тяжёлым он становится только
пачкой — в волне реконнекта.

## Массовый реконнект

Рестарт API (любой деплой) рвёт все соединения, и клиенты возвращаются разом.
Как это выглядит на 2000 клиентах — по срезам в [load-testing.md](load-testing.md):

1. **Остановка ~10 с.** API ждёт закрытия всех WebSocket и упирается в таймаут
   остановки Docker (10 с), после чего получает SIGKILL. События из outbox при этом
   не теряются (доставка «хотя бы один раз»), но деплой длиннее, чем мог бы быть.
2. **API готов, клиентов нет ~20 с.** Попытки, начатые, пока API лежал, висят в Caddy;
   следующие приходят по расписанию клиента (0, 2, 5, 10, 30 с).
3. **Волна подключений** — API на 99% CPU: на каждое подключение — рассылка «в сети»
   всем собеседникам.
4. **Волна списков чатов** — Postgres на 99%: каждый клиент перечитывает список.

Что улучшит, по порядку отдачи:

| # | Что | Где |
|---|---|---|
| 1 | Случайный разброс (jitter) в паузах переподключения клиента — волна размажется | клиент |
| 2 | ~~После реконнекта — `GET /api/sync?since=` вместо полного списка чатов~~ — сделано: веб-клиент догоняет журнал | клиент |
| 3 | `stop_grace_period` / `HostOptions.ShutdownTimeout` короче, чтобы API не ждал 10 с и не получал SIGKILL | compose + `Program.cs` |
| 4 | `lb_try_duration` в Caddy: запросы во время рестарта ждут API несколько секунд, а не висят и не получают 502 | `deploy/Caddyfile` |
| 5 | Дешевле рассылка «в сети» при подключении (пачкой, с задержкой) | `PresenceService` |

Пункты 1–2 — самые действенные: они убирают и ожидание, и пик нагрузки.

## Ограничения, которые настройкой не лечатся

- **Один инстанс.** Presence и реестр соединений живут в памяти процесса, SignalR
  работает без backplane. Вторую реплику добавить нельзя — только вертикальный рост.
- **Деплой обнуляет присутствие.** После рестарта онлайн пропадает, пока клиенты не
  переподключатся (см. выше).

### Про `pg_stat_statements`

Нужен параметр запуска и рестарт Postgres:

```yaml
postgres:
  command: >
    postgres -c shared_preload_libraries=pg_stat_statements
             -c pg_stat_statements.track=all
```

и затем `CREATE EXTENSION IF NOT EXISTS pg_stat_statements;` (можно миграцией).
Памяти берёт немного, но при `limits.memory: 768M` это стоит держать в голове.

# Бэкенд: ревью и план доработок

Цель: довести проект от «работающего пета» до бэкенда мессенджера, который не стыдно
выкатить. Фронт в этом плане не трогаем — только API, хаб, БД и инфраструктура.

**Позиционирование:** приватный мессенджер для команд и сообществ, который можно
развернуть у себя (self-hosted). Группы и рабочие сценарии плюс приватность и контроль
над данными. Ориентиры по функциям — Element/Matrix, Wire, Mattermost; по UX — Telegram.
Отличаемся простотой установки: один docker-compose и один Postgres.
Подробности — в части 2.

Состояние на 2026-09-29, коммит `e6d4069`. Сборка чистая, 152 юнит-теста зелёные.

Документ дополняет [project-analysis.md](../project-analysis.md), а не заменяет его.
Оттуда уже закрыто: секреты вне git, уязвимый `Microsoft.OpenApi`, CORS, rate limiting
на auth, 409 при гонке регистрации, `last_login_at`. Открытые пункты оттуда ниже
упоминаются со ссылкой `PA#N`.

Приоритеты:

- 🔴 **Крит** — дыра в безопасности, потеря или порча данных, или без этого продукт
  не является мессенджером.
- 🟠 **Мажор** — нужно до реальных пользователей, но вокруг можно временно обойтись.
- 🟡 **Минор** — качество, удобство, задел на будущее.

## Часть 1. Ревью: проблемы в существующем коде

### 🔴 Крит

**R1. SignalR-соединение живёт вечно после истечения токена, logout и деактивации.**
Хаб проверяет access-токен только при подключении. `MapHub` вызывается без
`CloseOnAuthenticationExpiration`, а `logout-all` и деактивация не рвут соединения.
Итог: украденный токен, отозванная сессия или заблокированный аккаунт продолжают
получать и отправлять сообщения, пока сокет не упадёт сам.
[Program.cs:166](../BasicApi/Program.cs#L166)
*Что делать:* `MapHub<ChatHub>("/hubs/chat", o => o.CloseOnAuthenticationExpiration = true)`;
в `logout-all` и при деактивации рвать соединения пользователя. Для этого нужен реестр
`userId → connectionIds` (он уже есть в `UserStatusService`) и серверный `Abort`
(например, через событие `ForceDisconnect` плюс `Context.Abort()` в хабе).

**R2. `Typing` не проверяет членство в чате.**
Любой авторизованный пользователь, знающий `chatId`, шлёт `TypingChanged` всем
участникам чужого чата. Заодно `_typingByChat` пополняется произвольными `chatId`,
а записи в ней не истекают (PA#22) — это неограниченный рост памяти.
[ChatHub.cs:239](../BasicApi/Hubs/ChatHub.cs#L239)
*Что делать:* `IsMemberAsync` (или кэш членства на соединение) до любых действий,
TTL на typing (5–7 с), очистка в `OnDisconnectedAsync`.

**R3. Необработанные исключения не логируются.**
`ExceptionHandlingMiddleware` превращает любое исключение в 500 и нигде его не
пишет: `ILogger` в нём нет. В продакшене причина любой 500-ки теряется.
[ExceptionHandlingMiddleware.cs:65](../BasicApi/Middleware/ExceptionHandlingMiddleware.cs#L65)
*Что делать:* `logger.LogError(ex, ...)` с `traceId`, 4xx — на уровне `Debug`/`Information`.
Ещё проверять `Response.HasStarted`, иначе запись в уже начатый ответ падает второй раз.

**R4. Нет прод-периметра: TLS и `ForwardedHeaders`.**
Прод-compose публикует голый HTTP на 8080, а access-токен для хаба уходит в query
string, то есть открытым текстом. Если поставить reverse proxy для TLS, сломается
другое: без `UseForwardedHeaders` все клиенты придут с IP прокси, и глобальный лимит
«60 запросов в минуту с IP» станет лимитом на весь сервис. Туда же — IP в сессиях и логах.
[ServiceExtensions.cs:397](../BasicApi/Extensions/ServiceExtensions.cs#L397),
[docker-compose.prod.yml](../docker-compose.prod.yml)
*Что делать:* Caddy или nginx с TLS в compose; `ForwardedHeadersOptions` с явным
`KnownProxies`/`KnownNetworks`; API опубликовать только на `127.0.0.1`.

**R5. Нет fail-fast на слабый или дефолтный JWT-ключ.**
В `appsettings.json` лежит рабочий плейсхолдер `your-super-secret-key-...`. Если
в проде не задать `Jwt__Key`, приложение молча стартует с этим ключом, и любой
читатель репозитория выпускает токены за любого пользователя.
[appsettings.json](../BasicApi/appsettings.json)
*Что делать:* вне `Development` падать на старте, если ключ совпадает с плейсхолдером
или короче 32 байт. Плейсхолдер вынести в `appsettings.Development.json`.

### Защита от XSS через чужой контент

В мессенджере пользователи доставляют свой контент прямо на страницы друг друга.
Если клиент отрисует его как код, скрипт одного пользователя выполнится в браузере
другого — с его токенами и чатами. Фронт сейчас защищён хорошо: нет `v-html`,
access-токен только в памяти, есть CSP в `<meta>`. Но полагаться только на клиент
нельзя: клиентов будет несколько.

## Часть 2. Позиционирование и модель приватности

### Для кого продукт

Сочетание двух сегментов:

- **Команды и организации (C)** — группы, каналы-объявления, треды, поиск, интеграции,
  администрирование, SSO.
- **Приватное общение (B)** — контроль над данными, настройки приватности, блокировки,
  исчезающие сообщения.

Следствия для архитектуры:

- **Одна установка = одна организация (single-tenant).** `tenant_id` не закладываем.
  Если понадобится SaaS — отдельный инстанс на клиента.
- **Регистрацией управляет администратор инстанса:** открытая, по приглашениям или
  только через SSO.
- **Всё, что нужно для работы, ставится вместе с продуктом:** Postgres, MinIO,
  LiveKit и coturn для звонков. Внешние облачные сервисы допустимы только как опция —
  исключение одно: push на мобильные идёт через FCM/APNs.
- **Эксплуатация — часть продукта.** Бэкап, восстановление, обновление и установка
  документированы и проверены, потому что обслуживать сервер будет не наша команда.

### Модель приватности

Сервер принадлежит организации, и пользователи доверяют ему содержимое переписки.
Приватность обеспечивается слоями:

1. **Транспорт** — TLS везде (R4).
2. **Контроль над данными** — данные не покидают сервер организации.
3. **Минимизация** — ограниченный срок хранения IP и User-Agent в сессиях и логах,
   политики хранения сообщений, исчезающие сообщения, никаких текстов сообщений в логах.
4. **Шифрование хранения** — тома БД и файлов, зашифрованные бэкапы, SSE в MinIO.
5. **Приватность между пользователями** — видимость last seen и online, кто может
   писать и добавлять в группы, блокировки.
6. **Защита от других пользователей** — строгая авторизация на каждом эндпоинте и
   методе хаба; контент одного пользователя никогда не исполняется на странице
   другого (R29–R34).

### E2E: сознательно не делаем

Решение принято 2026-09-29. E2E нужно ровно для одного — чтобы пользователю не
приходилось доверять серверу. Для нас это не окупается:

- **Оператор сервера — сама организация.** Сотрудник и так доверяет работодателю,
  а рабочая переписка часто принадлежит компании. Корпоративному сегменту обычно
  нужно обратное: архив по требованию юристов, DLP, передача переписки при увольнении.
- **Основной клиент — веб.** Код клиента отдаёт тот же сервер, поэтому доверие
  к серверу никуда не переносится, и гарантии E2E в браузере номинальные.
- **E2E отключает серверные функции:** поиск, превью в списке чатов и в push, превью
  ссылок, серверных ботов, модерацию, превью файлов, историю на новом устройстве,
  историю после сброса пароля.
- **Цена:** мультидевайс, верификация ключей, криптографический аудит.

Серверную логику, которая читает текст сообщений (поиск, превью, текст в push, превью
ссылок), всё равно держим отключаемой. Это гигиена приватности и настройка для
администратора, а не подготовка к E2E. Вернуться к вопросу стоит, если появится
общий (не корпоративный) инстанс и нативный клиент с подписанными сборками.

## Часть 3. Ключевые архитектурные решения

Эти решения дорого менять потом, поэтому принимаются до реализации фич.

**A1. Журнал обновлений на пользователя + `/sync`.**
Каждое изменение, которое должен узнать пользователь, пишется в `user_updates` с
монотонным номером `pts` на пользователя: новое сообщение, правка, удаление, прочтение
на другом устройстве, добавление в группу, смена прав, закрепление. Клиент после
реконнекта или на новом устройстве вызывает `GET /api/sync?since=pts` и получает
разницу. Если разрыв слишком большой — ответ «перезагрузи состояние». SignalR — лишь
быстрый канал доставки тех же записей, а не источник правды. Хранение ограничено по
сроку (например, 30 дней). Для больших каналов (тысячи участников) запись каждому
заменяется счётчиком на канал: клиент синхронизирует такие чаты по `seq` чата.

**A2. Модель сообщения.**
`seq` (монотонный внутри чата), `client_message_id` (идемпотентность), `type`
(`text` / `media` / `system` / `poll` / …), `text`, `entities` (разметка и упоминания
как смещения в тексте, не markdown), `content jsonb` (данные конкретного типа),
`reply_to_message_id`, `forward_from_*`, `edited_at`, `deleted_at`.
Новый тип сообщения — это новая схема `content`, а не миграция.

**A3. Файлы отдельно от сообщений.**
MinIO, загрузка по presigned URL, таблица `attachments`. Сообщения, аватары и стикеры
только ссылаются на файл. Отсюда пересылка без повторной загрузки, медиа-галерея чата
и единые лимиты и проверки.

**A4. Устройство как сущность.**
Устройство = сессия + платформа + push-токен. Нужно для push,
входа по QR, списка устройств и отзыва конкретного устройства.

**A5. Статусы сообщения: «отправлено», «доставлено», «прочитано».**
Хранятся как два указателя на участника — `last_delivered_seq` и `last_read_seq`, —
без записи на каждое сообщение. «Доставлено» — хотя бы одно устройство получателя
подтвердило получение через `POST /api/sync/ack`. Изначально решение было «без
доставлено»; пересмотрено 2026-09-29, когда статус вошёл в объём функций: на журнале
обновлений он получается дёшево.

**A6. Права в группах.**
Роли `owner` / `admin` / `member` + набор прав на роль (писать, отправлять медиа,
добавлять и удалять участников, удалять чужие сообщения, менять настройки, назначать
админов) + переопределения на участника. Все проверки — через единую точку
`IChatPolicy`.

**A7. События через outbox.**
Доменная операция и запись события в `user_updates` / outbox — в одной транзакции.
Рассылка в SignalR, push и вебхуки идёт из outbox фоновым обработчиком. Сейчас
сообщение пишется в БД, а событие отправляется отдельно: падение между этими шагами
теряет событие.

**A8. Транспорт: команды через REST, сокет только для событий.**
Клиент выполняет действия (отправка, правка, реакции, typing) через REST, а сокет
только доставляет события от сервера. Гарантии доставки дают журнал и `/sync` (A1),
а не транспорт. Поэтому транспорт заменяем: SignalR сейчас, при необходимости — чистый
WebSocket, SSE или long polling; меняется только адаптер `IChatEventPublisher`.
REST-команды получают валидацию, rate limiting, идемпотентность и ProblemDetails
бесплатно. Та же модель у Slack.

# Нагрузочный прогон

Базовые цифры — точка отсчёта для сравнения после изменений. Инструмент —
[`tools/BasicApi.LoadTest`](../tools/BasicApi.LoadTest), данные — его `seed.sql`.
Выводы для эксплуатации — в [capacity-and-limits.md](capacity-and-limits.md).

## Что делает прогон

1. **Данные.** `seed.sql` создаёт N пользователей; у каждого 2 × K личных чатов с
   соседями по кругу и по M сообщений в каждом чате, у второго участника по два
   непрочитанных. Идентификаторы детерминированные (md5 от номера), у каждого
   пользователя — живой вход (сессия).
2. **Подключение.** Программа выпускает access-токены сама (ключ подписи стека, `sid`
   входа из сида) — bcrypt логина и лимит auth-политики не участвуют — и подключает
   к хабу первых C пользователей через Caddy (HTTPS, WebSocket), по 50 одновременно.
3. **Штатный поток.** Открытый поток (не «запрос за запросом»): R отправок в секунду
   через `POST /api/chats/{id}/messages` в случайный чат случайного подключённого
   пользователя и L открытий списка чатов (`GET /api/chats`). Задержка доставки —
   от отправки до прихода `ChatListUpdated` получателю (время отправки — в тексте
   сообщения, часы одни). Каждые 10 секунд — загрузка контейнеров (`docker stats`).
4. **Массовый реконнект** (`--restart-container`): `docker restart` API; клиенты
   переподключаются с паузами веб-клиента (0, 2, 5, 10, 30 с) и после реконнекта
   берут список чатов — как перезагрузка страницы. Меряется, когда вернулся каждый
   клиент и сколько шёл его список чатов.

## Как запустить

```powershell
# прод-стек локально (docs/deploy.md, «Прод-стек локально»)
docker compose --env-file .env.local -f docker-compose.prod.yml -f docker-compose.local.yml up -d --build

# данные: 2000 пользователей × 20 чатов × 20 сообщений (~35 с, ~225 МБ)
Get-Content tools/BasicApi.LoadTest/seed.sql | docker exec -i basicchat_postgres `
    psql -U <DB_USER> -d <DB_NAME> -v users=2000 -v peers=10 -v messages=20

# прогон
dotnet run --project tools/BasicApi.LoadTest -c Release -- `
    --base-url https://localhost:8443 --insecure --jwt-key <JWT_KEY> `
    --users 2000 --peers 10 --connections 1000 --send-rate 40 --list-rate 20 --duration 60 `
    --restart-container basicchat_api --stats basicchat_api,basicchat_postgres,basicchat_caddy

docker compose --env-file .env.local -f docker-compose.prod.yml -f docker-compose.local.yml down -v
```

Против прода не запускать: сид пишет в базу пользователей с нерабочими паролями, а
ключ подписи прода не должен покидать сервер.

## Результаты, 2026-09-30

Стенд: прод-compose с его лимитами (API 1 CPU / 512 МБ, Postgres 1 CPU / 768 МБ,
пул Npgsql 30), Docker Desktop (WSL2) на Windows 10, 16 логических CPU. Генератор
нагрузки на той же машине — цифры с запасом в худшую сторону. Данные: 2000
пользователей, 20 000 чатов, 40 000 участников, 400 000 сообщений (225 МБ).
Коммит — `8e05a3e`.

### Штатный поток

Задержки в мс: p50 / p95 / p99. Ошибок и потерянных событий нет ни в одном прогоне:
каждое `ChatListUpdated` дошло до каждого подключённого получателя.

| Клиентов | Поток | Отправка | Список чатов | Доставка | API CPU / RAM | Postgres CPU | Caddy CPU / RAM |
|---|---|---|---|---|---|---|---|
| 250 | 10 отпр/с, 5 спис/с | 8 / 25 / 208¹ | 5 / 11 / 82¹ | 8 / 26 / 238¹ | низкая / 93 МБ | низкая | — |
| 500 | 20 / 10 | 8 / 12 / 26 | 4 / 8 / 14 | 8 / 12 / 26 | 11% / 123 МБ | 10% | — |
| 1000, Caddy 128 МБ | 40 / 20 | 29 / 74 / 89 | 23 / 69 / 80 | 30 / 73 / 83 | 20% / 143 МБ | 18% | **50% (упор) / 124 из 128 МБ** |
| 1000, Caddy 512 МБ | 40 / 20 | 8 / 12 / 29 | 5 / 7 / 15 | 8 / 12 / 30 | 20% / 148 МБ | 19% | 5% / 250 МБ |
| 2000, Caddy 512 МБ | 80 / 40 | 13 / 44 / 91 | 10 / 35 / 63 | 12 / 43 / 106 | 52% / 159 МБ | 40% | 26% / 425 МБ |

¹ первый прогон на свежем стеке: прогрев (JIT, пул соединений). Повтор той же нагрузки
в следующей строке — без хвоста.

Подключение к хабу (negotiate + WebSocket + TLS), по 50 одновременно: p95 0,3 с на
1000 клиентах, 0,8 с на 2000.

### Массовый реконнект после `docker restart` API

| Клиентов | Остановка + старт | Вернулись: 50% / 100% | Список чатов после реконнекта: p50 / max | Ошибки |
|---|---|---|---|---|
| 1000, Caddy 128 МБ | 2 с | 17–19 с / 25–29 с | 4,3–4,6 с / 7,9–10,7 с | 11 × 502 |
| 1000, Caddy 512 МБ | 2 с | 9,7 с / 10,8 с | 1,5 с / 2,4 с | нет |
| 2000, Caddy 512 МБ | 10–11 с | 41–46 с / 74–87 с | 5,9–7,4 с / 12–13,5 с | нет |

Клиенты не сдались ни разу (веб-клиент сдаётся после пяти неудачных попыток).

Как идёт реконнект 2000 клиентов (срез каждые 5 с):
- **0–11 с** — остановка: API ждёт закрытия 2000 WebSocket и упирается в таймаут
  остановки Docker (10 с), дальше SIGKILL.
- **11–32 с** — API уже готов, но никто не подключён: попытки, начатые, пока API
  лежал, висят в Caddy; следующие приходят по расписанию клиента.
- **32–48 с** — волна подключений: API 99% CPU (1400 подключений за 5 с, на каждое —
  рассылка «в сети» собеседникам).
- **48–58 с** — волна списков чатов: Postgres 99% CPU (~1800 запросов списка за 5 с).
- **58–87 с** — последние ~170 клиентов ждут своей попытки по расписанию (+47 с).

## Что нашёл прогон

- **Caddy упирался в свою память.** Около 220–250 КБ на открытый WebSocket; при
  лимите 128 МБ на 1000 клиентах Go-сборщик мусора работал без остановки и съедал
  весь лимит CPU — задержки выросли вчетверо, а до OOM-kill (падения всего входа)
  оставалось ~50 соединений. Лимиты Caddy подняты до 1 CPU / 512 МБ — хватает
  примерно на 2000 клиентов.
- **Каталог ключей Data Protection** (tmpfs) принадлежал root: после каждого рестарта
  API в логе была ошибка уровня Error. Каталог теперь принадлежит пользователю
  приложения.

## Точка отсчёта

- Штатный поток на 2000 клиентах занимает половину CPU API и 40% Postgres при
  80 отправках в секунду — запас есть.
- Слабое место — рестарт при большом числе клиентов: 1000 возвращаются за ~11 с,
  2000 — за полторы минуты. Что это улучшит — в
  [capacity-and-limits.md](capacity-and-limits.md#массовый-реконнект).
- Повторять прогон — после изменений в хабе, присутствии, списке чатов и доставке
  событий, и сравнивать с таблицами выше.

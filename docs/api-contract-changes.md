# Изменения контрактов API

Документ для клиентов (Android). Описывает изменения, сделанные по фидбеку
о том, что новый чат приходит без `companionId`, а онлайн-статус нельзя
запросить принудительно.

**Статус:** breaking. Публичного релиза не было, обратная совместимость не поддерживается.

## 1. `ChatListItemDto`: новое поле `companionUsername`

Единый тип для списка чатов, поиска чатов, `ChatCreated`, ответа на создание чата
и новой ручки `/item`.

```json
{
  "chatId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "type": "private",
  "title": null,
  "companionId": "0b2c...",
  "companionName": "Alice",
  "companionUsername": "alice",
  "lastMessage": null,
  "unreadCount": 0,
  "lastActivityAt": "2026-08-31T10:12:00Z"
}
```

- `companionId` / `companionName` / `companionUsername` заполнены только для `type: "private"`,
  для групп — `null`.
- Companion — всегда «второй участник с точки зрения того, кому отдаётся объект».
- `lastMessage` — `null`, если в чате ещё нет сообщений.

## 2. `POST /api/chats/private/{userId}`

**Было** — только id, клиенту нечего положить в список чатов:

```json
{ "chatId": "3fa85f64-..." }
```

**Стало** — полный `ChatListItemDto` (и для `201 Created`, и для `200 OK`, когда чат уже существовал):

```json
{
  "chatId": "3fa85f64-...",
  "type": "private",
  "title": null,
  "companionId": "0b2c...",
  "companionName": "Alice",
  "companionUsername": "alice",
  "lastMessage": null,
  "unreadCount": 0,
  "lastActivityAt": "2026-08-31T10:12:00Z"
}
```

Поле `chatId` осталось на месте и с тем же смыслом, так что старый парсинг «достать `chatId`»
продолжает работать. Companion в ответе — это **тот, с кем создали чат** (`{userId}` из пути).

## 3. SignalR `ChatCreated`

**Было** — два аргумента, и в `companionName` лежало имя *самого получателя* (баг):

```
ChatCreated(chatId: Guid, dto: ChatCreatedEventDto)
```

**Стало** — один аргумент, готовый элемент списка:

```
ChatCreated(item: ChatListItemDto)
```

- `chatId` теперь внутри тела (`item.chatId`).
- Payload собирается **отдельно для каждого получателя**: в `companionId`/`companionName`/
  `companionUsername` лежит создатель чата, а не сам получатель.
- Тип `ChatCreatedEventDto` удалён.

Клиенту достаточно вставить `item` в список чатов как есть и вызвать `JoinChat(item.chatId)` —
дополнительный запрос не нужен.

---

## 4. `GET /api/chats/{chatId}/item` (новая)

Возвращает один чат в форме элемента списка — тот же `ChatListItemDto`, что отдаёт `GET /api/chats`,
собранный для вызывающего.

- `200` — тело `ChatListItemDto`
- `403 NOT_A_MEMBER` — вызывающий не участник чата
- `404 CHAT_NOT_FOUND` — чата нет

Когда использовать: клиент знает только `chatId` (пуш, deep link, событие `ChatListUpdated`)
и хочет отрисовать/обновить ровно одну строку, не перезапрашивая весь список.

Существующая `GET /api/chats/{chatId}` не изменилась — она по-прежнему отдаёт `ChatDetailDto`
со списком участников. Нужен список участников — берите её, нужна карточка для списка — `/item`.

---

## 5. `GET /api/users/{userId}/status` (новая)

Онлайн-статус одного пользователя.

```json
{ "userId": "0b2c...", "isOnline": true }
```

- Оффлайн отдаётся **явным** `"isOnline": false`, а не отсутствием записи.
- `404 USER_NOT_FOUND` — если у вас нет общего чата с этим пользователем.
  Тот же код возвращается и для несуществующего аккаунта: по ручке нельзя проверить,
  зарегистрирован ли кто-то.
- Свой собственный id запрашивать можно.

Когда использовать: вход на экран чата. Событие `UserOnlineChanged` могло сработать,
пока приложение было закрыто, поэтому текущее состояние нужно спросить самому.

---

## 6. `POST /api/users/status` (новая, батч)

```
POST /api/users/status
{ "userIds": ["0b2c...", "7f1a..."] }
```

```json
{
  "items": [
    { "userId": "0b2c...", "isOnline": true },
    { "userId": "7f1a...", "isOnline": false }
  ]
}
```

- Отдаёт запись на каждого запрошенного пользователя, **включая оффлайн**.
- Пользователи, с которыми у вас нет общего чата, молча выпадают из ответа.
- Максимум 200 id за запрос (`400 TOO_MANY_IDS`), пустой список — `400 INVALID_REQUEST`.
  Дубликаты схлопываются.

Когда использовать: вход на экран списка чатов — отправить `companionId` видимых приватных
чатов и получить их статусы одним запросом.

### Отличие от существующей `GET /api/users/status`

`GET /api/users/status` не изменилась: она возвращает **только онлайн** участников
всех ваших чатов, без возможности задать список. Отсутствие пользователя в её ответе
означает «оффлайн». Новые ручки нужны, когда важен явный `false` и точечный набор id.

## 7. Bugfix: `GET /api/chats/search`

Поиск чатов терял `companionId` и `companionUsername` при маппинге — приватные чаты
из результатов поиска приходили без id собеседника. Починено; маппинг списка чатов
и поиска теперь общий, так что расхождение не вернётся.

---

## Что осталось на клиенте

Сервер по-прежнему **не** пушит снапшот онлайна при подключении к хабу, и в
`ChatListItemDto` **нет** поля `isOnline`. После реконнекта/холодного старта клиент
обязан сам запросить статусы (п. 5 и 6) — иначе собеседники будут показаны оффлайн
до первого события `UserOnlineChanged`.

## 8. Авторизация: session + refresh token

Раньше `login`/`register` отдавали один JWT на сутки, а `logout` не делал ничего.
Теперь это полноценные сессии с ротацией.

### Что изменилось в ответе login/register

**Было:**

```json
{
  "userId": "...", "username": "alice", "email": "...", "displayName": "Alice",
  "token": "eyJ...",
  "expiresAt": "2026-09-01T10:00:00Z"
}
```

**Стало** — добавились два поля:

```json
{
  "userId": "...", "username": "alice", "email": "...", "displayName": "Alice",
  "token": "eyJ...",
  "expiresAt": "2026-08-31T10:30:00Z",
  "refreshToken": "9f2c...",
  "refreshTokenExpiresAt": "2026-09-30T10:00:00Z"
}
```

- `token` (access) живёт **30 минут** вместо суток. Это осознанно: отзыв сессии
  должен срабатывать быстро.
- `refreshToken` живёт **30 дней** и меняется при каждом обновлении.
- Хранить надо оба. `refreshToken` не отправлять никуда, кроме `POST /api/auth/refresh`.

### `POST /api/auth/refresh` (новая)

```
POST /api/auth/refresh
{ "refreshToken": "9f2c..." }
```

Отдаёт такое же тело, как login. Ручка анонимная — протухший access-токен не нужен
и не принимается как доказательство чего-либо.

**Ротация.** Каждый успешный вызов гасит присланный refresh-токен и возвращает новый.
Всегда сохраняйте новое значение.

**Параллельные refresh безопасны.** Токен, ротированный менее **30 секунд** назад,
продолжает работать. Это ровно тот случай, когда приложение отправило два запроса
разом, оба получили 401 и оба пошли обновляться — проигравший не будет разлогинен.
Специально делать single-flight на клиенте не требуется.

**Переиспользование после этого окна = кража.** Гасится вся цепочка ротаций этого
логина, включая ту сессию, которой сейчас пользуются. Другие устройства не задеты.

Ошибки — все с кодом 401, различаются полем `errorCode`:

| errorCode | Когда |
|---|---|
| `INVALID_REFRESH_TOKEN` | токен не найден |
| `REFRESH_TOKEN_EXPIRED` | истёк срок (30 дней) |
| `SESSION_REVOKED` | по сессии сделали logout |
| `REFRESH_TOKEN_REUSED` | токен предъявлен повторно после grace-окна |
| `USER_INACTIVE` | аккаунт деактивирован |
| `USER_NOT_FOUND` | аккаунт удалён |

Для клиента все шесть означают одно: показать экран логина. Различать их нужно
только для логов и диагностики.

### `POST /api/auth/logout` — теперь действительно выходит

**Было:** пустая ручка, токен продолжал работать до истечения.
**Стало:** принимает тело и гасит сессию.

```
POST /api/auth/logout
Authorization: Bearer {access}
{ "refreshToken": "9f2c..." }
```

Без `refreshToken` в теле серверу нечего гасить — сессия останется живой. Так что
присылать его нужно всегда.

Идемпотентна: неизвестный или уже погашенный токен тоже даёт 200 — по ручке нельзя
проверить, существует ли токен. Access-токен продолжит работать до истечения
(до 30 минут) — выбрасывайте его на клиенте сами.

### `POST /api/auth/logout-all` (новая)

Гасит все сессии пользователя на всех устройствах. Нужна после смены пароля или
при потере устройства. Уже выданные access-токены доживают свой срок.

### Что это меняет для SignalR

Хаб авторизуется access-токеном **один раз** при подключении и сам его не обновляет.
Теперь, когда access живёт 30 минут, это стало заметно:

- живое соединение продолжает работать со старым токеном, пока не оборвётся;
- при реконнекте со старым токеном будет отказ.

Порядок для клиента: обновить токен через `refresh`, затем переподключить хаб с новым
`access_token`. Если refresh вернул 401 — это логаут, соединение восстанавливать не надо.

### Прочее

- `login` больше не пускает деактивированные аккаунты (`USER_INACTIVE`, 401), даже
  с верным паролем.
- Гонка при регистрации теперь отдаёт `409 USER_ALREADY_EXISTS`, а не `500`.
- `GET /api/auth/validate` не изменилась, но говорит только про access-токен.
  Её ответ ничего не сообщает о сессии: `isValid: false` не означает «надо логиниться»
  — сначала пробуйте `refresh`.

## 9. Исправления плана 1, этап 1

Всё ниже — без поломки контракта: новые коды ошибок и исправленное поведение.

### 9.1. Хаб закрывает соединение при потере доступа

- Соединение живёт, пока жив **вход** (сессия), с которого оно открыто, а не
  access-токен: истечение access-токена соединение не закрывает. (Сначала
  закрывало, но текущий веб-клиент при переподключении отдаёт тот же, уже
  истёкший токен и оставался без событий до перезагрузки страницы — найдено
  ручной проверкой в этапе 3.) Если вход закончился иначе — цепочка отозвана
  при повторе refresh-токена или истекла, — соединение закрывается в течение
  минуты. Переподключаться клиенту по-прежнему нужно со свежим токеном.
- `POST /api/auth/logout` закрывает соединения этого входа (устройства),
  `POST /api/auth/logout-all` — все соединения пользователя.
- Переподключиться со старым access-токеном закрытой сессии нельзя: сервер
  обрывает соединение сразу после подключения. Для клиента это то же, что
  отказ refresh, — показать экран входа.
- В access-токене появился claim `sid` — идентификатор входа (цепочки сессий).
  Клиенту он не нужен.

### 9.2. Typing

- `Typing(chatId, …)` от не-участника чата — ошибка `NOT_A_MEMBER` (раньше
  рассылалась всем участникам чужого чата).
- **Ошибки методов хаба** приходят как `HubException` с кодом. SignalR добавляет
  к тексту свой префикс, поэтому клиент получает:
  `"An unexpected error occurred invoking 'Typing' on the server. HubException: NOT_A_MEMBER: User is not a member of this chat"`.
  Код — слово сразу после `HubException: `, например так:
  `/HubException: ([A-Z_]+):/`.
- «Печатает» живёт **6 секунд** без повторного `Typing(true)`: пока пользователь
  набирает текст, клиент повторяет вызов раз в 3–4 секунды. `GET /api/users/typing`
  не показывает протухшие записи.
- Когда у пользователя закрывается последнее соединение, участники чатов, где он
  печатал, получают `TypingChanged(chatId, userId, false)`.

### 9.3. Отправка сообщения и вход в чат: ошибки вместо тишины

Раньше `SendMessage` и `JoinChat` при нарушении правил просто ничего не делали.
Теперь — `HubException` с кодом (как его достать из текста — в 9.2):

| Код | Когда |
|---|---|
| `MESSAGE_EMPTY` | текст пустой или из одних пробелов |
| `MESSAGE_TOO_LONG` | длиннее 4096 символов после обрезки пробелов |
| `NOT_A_MEMBER` | отправитель / входящий не участник чата |
| `RATE_LIMITED` | больше 20 вызовов за 10 секунд на соединение (было без кода) |

Пробелы и переводы строк по краям текста обрезаются; сохраняется и рассылается
уже обрезанный текст.

### 9.4. `POST /api/chats/private/{userId}`

- Несуществующий или деактивированный собеседник — `404 USER_NOT_FOUND`
  (раньше `500`).
- Один личный чат на пару гарантирует база: двойной клик или два устройства
  больше не создают два чата. Первый вызов — `201`, повторные — `200` с тем же чатом.
- При обновлении сервера уже существующие дубли личных чатов сливаются в самый
  старый: сообщения переносятся, id дублей перестают существовать. Клиенту стоит
  перезагрузить список чатов после обновления.

### 9.5. Логин и email без учёта регистра

- `login` принимает логин или email в любом регистре и с пробелами по краям:
  `Alice`, `alice`, ` ALICE ` — один пользователь.
- `register`: логин или email, отличающийся от занятого только регистром, —
  `409 USERNAME_TAKEN` / `EMAIL_TAKEN`. Пробелы по краям обрезаются.
- В ответах логин и email — в том регистре, в котором их ввели при регистрации.

### 9.6. Прочитанность

- `unreadCount` больше не включает **собственные** сообщения пользователя.
- `POST /api/chats/{chatId}/read` с сообщением из другого чата или несуществующим —
  `404 MESSAGE_NOT_FOUND` (раньше указатель вставал на чужое сообщение).
- Указатель прочитанного двигается **только вперёд**: отметка более старого
  сообщения (например, с другого устройства) отвечает `200` и ничего не меняет.
- Сообщения с одинаковым временем упорядочены по `id` — так же, как в пагинации.

### 9.7. Пагинация, поиск, переход к дате, вход

- `GET /api/chats/{chatId}/messages/at?date=…` **работает**: раньше всегда
  возвращал пустую страницу. Страница заканчивается последним сообщением на момент
  `date` **включительно**. Дата принимается с любым смещением (`…Z`, `…+03:00`).
  Не-участник — `403 NOT_A_MEMBER` до любых обращений к сообщениям.
- Битый или подделанный `cursor` — `400 INVALID_CURSOR` (раньше `500`).
- `nextCursor` = `null`, когда `hasMore` = `false` (раньше был курсор в пустоту).
- Поиск по сообщениям: `totalCount` одинаковый на всех страницах (раньше `0`
  начиная со второй).
- `register`: пароль длиннее 72 байт в UTF-8 — `400 PASSWORD_TOO_LONG`
  (bcrypt не учитывает байты дальше 72-го). Для кириллицы это 36 символов.
- `login` отвечает за одинаковое время независимо от того, существует ли логин.

### 9.8. `GET /api/users/GetUserId/{username}` — только по логину

- Поиск **по email убран**: по чужой почте нельзя узнать, есть ли у человека
  аккаунт, и получить его id. Запрос с email теперь `404 USER_NOT_FOUND`.
- Логин — без учёта регистра; деактивированные пользователи — `404`.
- Путь не изменился, изменилось только имя параметра в документации.

### 9.9. Онлайн-статус в новом личном чате

Когда создаётся новый личный чат, каждый из двоих, если собеседник в сети,
получает `UserOnlineChanged(userId, true)` о нём. Раньше статус приходил только
при подключении к хабу и только от тех, с кем уже был общий чат, поэтому в новом
чате оба видели друг друга «не в сети» до перезагрузки.

## 10. План 1, этап 2

Всё здесь — добавления: старые ручки, методы и события хаба работают как раньше.

### 10.1. Команды через REST

Хаб становится каналом событий, а команды переезжают в REST. Методы хаба
`SendMessage` и `Typing` остаются и работают через те же сервисы — переезжать
можно постепенно.

**`POST /api/chats/{chatId}/messages`** — отправить сообщение.

```json
{ "text": "Привет" }
```

- `201` — `MessageDto` отправленного сообщения.
- Правила те же, что у `SendMessage`: пробелы по краям обрезаются, длина 1–4096.
- События те же: участникам (включая отправителя — его другим устройствам)
  приходят `MessageCreated` и `ChatListUpdated`.
- Ошибки: `400 MESSAGE_EMPTY`, `400 MESSAGE_TOO_LONG`, `403 NOT_A_MEMBER`,
  `429 RATE_LIMITED`.

**`POST /api/chats/{chatId}/typing`** — «печатает».

```json
{ "isTyping": true }
```

- `204`. Остальным участникам приходит `TypingChanged(chatId, userId, isTyping)`.
- «Печатает» гаснет через 6 секунд без повтора: пока пользователь набирает текст,
  повторять `true` раз в несколько секунд; перестал — `false`.
- Ошибки: `403 NOT_A_MEMBER`, `429 RATE_LIMITED`.

**Лимит.** На **пользователя** (все его устройства вместе): отправка — 20 за 10 секунд,
«печатает» — свои 20 за 10 секунд вместе с черновиками (см. 21.1). Превышение —
`429 RATE_LIMITED` с заголовком `Retry-After`. Это дополнительно к общему лимиту API.

### 10.2. Время — всегда UTC с `Z`

Все даты в ответах и событиях — в UTC с суффиксом `Z`:
`"createdAt": "2026-09-29T18:04:05.123456Z"`.

Раньше история сообщений, список чатов и поиск отдавали время **без** суффикса
(`"2026-09-29T18:04:05.123456"`), а события хаба — с ним. Строка без суффикса
читается как местное время; веб-клиент поэтому дописывал `Z` сам — теперь это
не нужно, но и не мешает. Кроме того, при часовом поясе сервера базы не UTC время
новых сообщений сохранялось со сдвигом — исправлено.

### 10.3. Номер сообщения `seq` и идемпотентная отправка

**`MessageDto` — два новых поля** (везде: история, поиск, `lastMessage` в списке
чатов, события `MessageCreated` и `ChatListUpdated`, ответ отправки):

```json
{
  "id": "…", "chatId": "…", "text": "Привет", "createdAt": "…Z",
  "seq": 42,
  "clientMessageId": "7d3b…"   // или null
}
```

- `seq` — номер сообщения в чате: 1, 2, 3, … Выдаётся сервером при сохранении,
  строго по порядку; сообщения чата упорядочены по нему (раньше — по времени, у
  которого бывали совпадения). Удалённые сообщения оставляют пропуски в номерах.
- `clientMessageId` — id, который клиент передал при отправке через REST.

**Отправка с `clientMessageId`.** `POST /api/chats/{chatId}/messages`:

```json
{ "text": "Привет", "clientMessageId": "7d3b…" }
```

Клиент создаёт новый Guid на каждое сообщение до отправки и повторяет его при
ретраях (обрыв сети, таймаут). Повтор с тем же `clientMessageId`:

- не создаёт второе сообщение и не рассылает событие ещё раз;
- отвечает `200` (а не `201`) с тем же сообщением — тот же `id` и `seq`;
- id, уже занятый сообщением этого пользователя в **другом** чате, —
  `409 CLIENT_MESSAGE_ID_CONFLICT`.

Своё сообщение, пришедшее в `MessageCreated` на другое устройство или в тот же
клиент раньше ответа на POST, узнаётся по `clientMessageId` — так временную
«отправляемую» копию можно заменить настоящей без дубля.

Без `clientMessageId` отправка работает как раньше. Метод хаба `SendMessage`
его не принимает.

**Курсоры.** `nextCursor` теперь другого формата (короче). Для клиента он
по-прежнему непрозрачная строка. Курсоры, полученные до обновления, продолжают
работать.

**Непрочитанные** считаются по `seq`; указатель прочитанного по-прежнему
двигается через `POST /api/chats/{chatId}/read` с `lastMessageId`.

### 10.4. Доставка событий

Формат событий хаба не изменился. Изменилось, как они доставляются:
`MessageCreated`, `ChatListUpdated` и `ChatCreated` сохраняются вместе с
сообщением или чатом и рассылаются из очереди. Что это значит для клиента:

- событие больше не теряется, если сервер перезапустился сразу после сохранения —
  оно уйдёт после старта;
- в редком случае (сбой ровно между рассылкой и отметкой о ней) событие может
  прийти **дважды** — повтор узнаётся по `id` сообщения или `chatId`;
- задержка события после ответа на REST-запрос — единицы миллисекунд.

`TypingChanged` и `UserOnlineChanged` — как раньше: сразу и без гарантий.

### 10.5. Синхронизация: `/api/sync`

Событие хаба, пришедшее, пока клиент был отключён (сеть, сон, перезапуск), раньше
терялось навсегда — оставалось перезагружать всё. Теперь у каждого пользователя
есть журнал изменений с нумерацией `pts` (1, 2, 3, … — у каждого пользователя своя).
Журнал хранится 30 дней.

**Как пользоваться.**

1. При первом запуске — снимок: `GET /api/sync/state`. Запомнить `pts`.
2. Работать как обычно по событиям хаба.
3. После любого переподключения — `GET /api/sync?since={pts}`, применить
   `updates` по порядку, запомнить новый `pts`, повторять, пока `hasMore`.
4. Ответ `snapshotRequired: true` — журнал уже не помнит так далеко: шаг 1.

**`GET /api/sync/state`** → `200`

```json
{ "pts": 128, "chats": [ /* ChatListItemDto, как GET /api/chats */ ] }
```

Снимок и `pts` согласованы: всё, что есть в `chats`, учтено в `pts`, и наоборот. С плана 2, Ф8
в снимке всё состояние пользователя — см. 19.1.

**`GET /api/sync?since=128&limit=100`** → `200`

```json
{
  "updates": [
    { "pts": 129, "type": "MessageCreated", "payload": { /* MessageDto */ }, "createdAt": "…Z" },
    { "pts": 130, "type": "ChatCreated",    "payload": { /* ChatListItemDto */ }, "createdAt": "…Z" }
  ],
  "pts": 130,
  "hasMore": false,
  "snapshotRequired": false
}
```

- `type` — имя события хаба, `payload` — тот же объект, что в этом событии.
  Обработчики событий можно переиспользовать.
- Сейчас в журнал пишутся `MessageCreated` (всем участникам чата, включая
  отправителя — для его других устройств) и `ChatCreated` (обоим участникам;
  создателю живое событие по-прежнему не приходит). «Печатает» и онлайн — нет.
- Изменение могло прийти и по хабу, и в журнале — повтор узнаётся по `id`
  сообщения или `chatId`.
- `limit` — 1…500, по умолчанию 100. Отрицательный `since` — `400 INVALID_PTS`.

**`POST /api/sync/ack`** → `204`

```json
{ "pts": 130 }
```

Устройство подтверждает, что получило журнал до `pts`. Устройство — это вход
(свой для каждого логина). Подтверждение двигается только вперёд; `pts` больше
последнего — `400 INVALID_PTS`. На этом в плане 2 будет построен статус «доставлено».

### 10.6. Поиск по сообщениям понимает русский

`GET /api/chats/{chatId}/messages/search` находит русские слова в других формах
и ищет по началу слова: «запуск» находит «запускаем» и «до запуска», «запу» — тоже
(удобно искать по мере набора). Раньше русские слова находились только в точности
как написаны. Английские — как раньше и тоже по началу слова («run» находит
«running», «runs»), в том числе в сообщениях, где языки смешаны. Слова запроса
должны встретиться все. Запрос из одних служебных слов («и в на») возвращает
пустой результат. Формат запроса и ответа не изменился.

## 12. План 2, Ф1: сообщения

Всё здесь — добавления. Старые события приходят как раньше; новые текущий веб-клиент
просто не слушает.

### 12.1. Правка и удаление

**`MessageDto` — два новых поля** (везде, где есть `MessageDto`):

```json
{ "id": "…", "text": "Привет", "seq": 42,
  "type": "text",
  "editedAt": "2026-09-30T10:15:00Z" }   // null — не редактировалось
```

- `type` — вид сообщения; пока всегда `text`, медиа и системные появятся позже.
  Сообщение незнакомого типа клиенту стоит показать заглушкой, а не падать.

**`PATCH /api/chats/{chatId}/messages/{messageId}`** — изменить текст.

```json
{ "text": "Исправленный текст" }
```

- `200` — `MessageDto` с новым текстом и `editedAt`.
- Только автор и только в течение 48 часов после отправки (настройка сервера
  `Messages:EditWindowHours`). Правила текста — как при отправке.
- Всем участникам (включая автора — для его других устройств) приходит
  **`MessageUpdated(message)`** — сообщение целиком. В журнал `/api/sync` — тоже.
- Тот же текст ещё раз — `200` без изменений и без события.
- Ошибки: `400 MESSAGE_EMPTY`, `400 MESSAGE_TOO_LONG`, `403 NOT_A_MEMBER`,
  `403 NOT_MESSAGE_AUTHOR`, `403 EDIT_WINDOW_EXPIRED`, `404 MESSAGE_NOT_FOUND`
  (нет в этом чате или удалено), `429 RATE_LIMITED`.

**`DELETE /api/chats/{chatId}/messages/{messageId}?forEveryone=true`** — удалить.

- `204`.
- `forEveryone=true` — у всех. Только автор и только в течение 48 часов
  (`Messages:DeleteWindowHours`). Сообщение пропадает из истории, поиска, превью в
  списке чатов и из непрочитанных у всех участников. Всем участникам приходит
  **`MessageDeleted`** с `forEveryone: true`.
- Без параметра — только у себя. Любой участник, любое сообщение, в любое время.
  Сообщение пропадает только у вызвавшего; `MessageDeleted` с `forEveryone: false`
  приходит только на его устройства.
- Повторное удаление — `204` без события.
- Ошибки: `403 NOT_A_MEMBER`, `403 NOT_MESSAGE_AUTHOR`, `403 DELETE_WINDOW_EXPIRED`,
  `404 MESSAGE_NOT_FOUND`, `429 RATE_LIMITED`.

Обе команды делят лимит команд с отправкой (20 за 10 секунд на пользователя).

**`MessageDeleted(deleted)`**:

```json
{ "chatId": "…", "messageId": "…", "seq": 42, "forEveryone": true }
```

Что делать клиенту:
- `MessageUpdated` — заменить сообщение по `id`; если это последнее сообщение чата —
  обновить превью в списке.
- `MessageDeleted` — убрать сообщение по `messageId`. Если оно было последним в чате —
  перезапросить строку списка: `GET /api/chats/{chatId}/item`. Непрочитанные тоже
  пересчитаются в этом ответе.
- Оба события приходят **на все соединения** участников, а не только в открытый чат
  (`JoinChat`): они нужны и для списка чатов.
- `ChatListUpdated` на правку и удаление **не** приходит: текущий клиент считает по нему
  непрочитанные.

Удалённое для всех в истории не показывается совсем (как в Telegram), поэтому в
номерах `seq` бывают пропуски — на них нельзя полагаться как на непрерывные.

### 12.2. Ответ и пересылка

**`MessageDto` — ещё два поля:**

```json
{
  "id": "…", "text": "Конечно",
  "replyTo": {                          // null — не ответ
    "messageId": "…", "senderId": "…", "senderName": "Алиса",
    "text": "Обедаем в полдень?",       // первые 100 символов (с «…», если длиннее)
    "deleted": false                    // true — исходное удалено у всех, text пустой
  },
  "forwardFrom": {                      // null — не пересланное
    "senderId": "…", "senderName": "Боб" // автор оригинала
  }
}
```

**Ответ.** `POST /api/chats/{chatId}/messages` принимает `replyToMessageId`:

```json
{ "text": "Конечно", "replyToMessageId": "…" }
```

- Сообщение, на которое отвечают, должно быть в этом же чате и не удалено у всех,
  иначе `400 REPLY_TARGET_NOT_FOUND`. Удалённое у себя — можно.
- Если исходное удалят позже, `replyTo` останется с `deleted: true` и пустым текстом.
- Метод хаба `SendMessage` ответы не поддерживает.

**Пересылка.** `POST /api/chats/{chatId}/messages/forward` — в чат `chatId`:

```json
{
  "fromChatId": "…",
  "messageIds": ["…", "…"],            // 1–100 разных
  "clientMessageIds": ["…", "…"]       // необязательно, по одному на сообщение
}
```

- `201` — `{ "items": [MessageDto, …] }`: новые сообщения в целевом чате, в исходном
  порядке (по `seq` источника, а не по порядку в запросе).
- Каждая копия — новое сообщение пересылающего с `forwardFrom` — автором оригинала. Для
  пересылки пересланного — самым первым автором, как в Telegram. `replyTo` не переносится.
- Участникам целевого чата на каждую копию приходят `MessageCreated` и `ChatListUpdated`,
  как при обычной отправке.
- С `clientMessageIds` повтор запроса ничего не создаёт и отвечает `200` с теми же копиями.
- Пересланное нельзя редактировать: `403 MESSAGE_NOT_EDITABLE`. Удалять — можно.
- Переслать можно только то, что пользователь видит: удалённое у всех или у себя —
  `404 MESSAGE_NOT_FOUND`.
- Ошибки: `400 INVALID_REQUEST` (пусто, повторяющиеся id, `clientMessageIds` другой
  длины), `400 TOO_MANY_MESSAGES`, `403 NOT_A_MEMBER` (в любом из двух чатов),
  `404 MESSAGE_NOT_FOUND`, `409 CLIENT_MESSAGE_ID_CONFLICT`, `429 RATE_LIMITED`.
  Один запрос пересылки — одна команда в лимите.

### 12.3. Форматирование и упоминания

**`MessageDto.entities`** — разметка поверх `text`, всегда массив (пустой — обычный текст):

```json
{
  "text": "@Боб посмотри доку",
  "entities": [
    { "type": "mention", "offset": 0, "length": 4, "userId": "…" },
    { "type": "link", "offset": 14, "length": 4, "url": "https://example.com/docs" }
  ]
}
```

| `type` | Доп. поле |
|---|---|
| `bold`, `italic`, `underline`, `strikethrough`, `spoiler`, `code` | — |
| `pre` — блок кода | `language` — необязательно, до 32 символов `A-Z a-z 0-9 + # - . _` |
| `link` — ссылка с текстом | `url` — абсолютный `http`, `https` или `mailto`, до 2048 символов |
| `mention` — упоминание | `userId` — участник этого чата |

- `offset` и `length` — в единицах **UTF-16**, как индексы строк в JavaScript, Kotlin/Java
  и `String.utf16` в Swift. Эмодзи вне BMP занимает две единицы.
- Сущности отсортированы по `offset`; вложенность (жирный внутри курсива) допустима.
- Поля, не относящиеся к типу, в ответе отсутствуют.

**Отправка и правка.** `POST /api/chats/{chatId}/messages` и `PATCH …/messages/{messageId}`
принимают `entities`. Смещения считаются по тексту **как он отправлен**: сервер обрежет
пробелы по краям и сдвинет сущности сам; часть сущности на обрезанных пробелах
отбрасывается. Правка заменяет разметку целиком: без `entities` — обычный текст.

Сервер проверяет (иначе `400 INVALID_ENTITIES`, текст ошибки — в `detail`):
- не больше 100 сущностей, диапазон внутри текста, известный тип;
- ссылка — только `http`, `https`, `mailto`: `javascript:`, `data:` и прочее отклоняются;
- упомянутый пользователь — участник чата.

Метод хаба `SendMessage` разметку не принимает.

**Счётчик упоминаний.** `ChatListItemDto` — новое поле `unreadMentionCount`: непрочитанные
сообщения, где упомянут пользователь (как `unreadCount`, по указателю прочтения). Своё
упоминание себя не считается. Правка, убравшая упоминание, и удаление сообщения снимают
его со счётчика. У пересланных сообщений разметка сохраняется, но упоминания в них никого
не уведомляют.

### 12.4. Реакции

Одна реакция пользователя на сообщение, как в WhatsApp: новая заменяет прежнюю. Набор
задаёт сервер (`Messages:Reactions`), по умолчанию: 👍 ❤️ 😂 😮 😢 🙏 👎 🔥 🎉.
«❤» без невидимого селектора варианта (U+FE0F) и «❤️» с ним — одна реакция.

**`MessageDto` — ещё два поля:**

```json
{
  "reactions": [ { "emoji": "🔥", "count": 2 }, { "emoji": "🎉", "count": 1 } ],
  "myReaction": "🔥"
}
```

- `reactions` — всегда массив, самые популярные первыми (при равенстве — какая появилась
  раньше).
- `myReaction` — своя реакция или `null`. Заполняется **только в истории и поиске**.
  В событиях (`MessageCreated`, `MessageUpdated`) — `null`: своё отслеживайте по
  `ReactionsChanged`.
- В `lastMessage` списка чатов реакций нет — это превью.

**`PUT /api/chats/{chatId}/messages/{messageId}/reactions`** — поставить.

```json
{ "emoji": "🔥" }
```

- `200` — `MessageReactionsDto` (как в событии, ниже).
- Та же реакция ещё раз — `200` без события.
- Ошибки: `400 INVALID_REACTION` (не из набора), `403 NOT_A_MEMBER`,
  `404 MESSAGE_NOT_FOUND` (нет в чате, удалено у всех или у себя), `429 RATE_LIMITED`.

**`DELETE /api/chats/{chatId}/messages/{messageId}/reactions`** — убрать свою. `204`;
без реакции — `204` без события.

**`ReactionsChanged(reactions)`** — всем участникам на все соединения и в журнал:

```json
{
  "chatId": "…", "messageId": "…",
  "reactions": [ { "emoji": "🔥", "count": 2 } ],   // сводка после изменения
  "userId": "…",                                   // кто изменил
  "emoji": "🔥"                                    // его реакция теперь; null — убрал
}
```

Клиенту: заменить `reactions` сообщения; если `userId` — свой, запомнить `emoji` как
`myReaction`. Удаление сообщения у всех убирает и его реакции.

### 12.5. «Избранное»

**`POST /api/chats/saved`** — открыть свой чат с самим собой.

- Первый вызов создаёт чат: `201`; дальше — `200` с тем же чатом.
- Тело — `ChatListItemDto`, как в `GET /api/chats`: `type: "saved"`, `title` и
  `companion*` — `null`. Название («Избранное», «Saved Messages») клиент подставляет сам.
- Дальше это обычный чат: отправка, пересылка в него, правка, удаление, реакции, поиск.
  Непрочитанных в нём не бывает — все сообщения свои.
- Другие устройства пользователя узнают о новом чате через журнал `/api/sync`
  (`ChatCreated`), живого события нет — как у создателя личного чата.
- Чат появляется в `GET /api/chats` у своего владельца. Клиенту стоит знать новый тип
  `saved`: текущий веб-клиент покажет такой чат без названия, но сам его не создаёт.

## 13. План 2, Ф2: статусы и черновики

Всё здесь — добавления.

### 13.1. Доставлено и прочитано

Статус есть только у **своих** сообщений:

| `status` | Когда |
|---|---|
| `sent` | сообщение сохранено на сервере |
| `delivered` | устройство другого участника получило его и подтвердило через `POST /api/sync/ack` |
| `read` | другой участник прочитал его (`POST /api/chats/{chatId}/read`) |

В группе статус меняет **первый** участник, получивший или прочитавший сообщение, как в
Telegram. В «Избранном» статуса нет.

**`MessageDto`:**

```json
{ "id": "…", "seq": 42, "senderId": "<я>",
  "status": "delivered",   // своё: sent / delivered / read; чужое — null
  "isRead": false }        // своё — status == read; чужое — прочитал ли его я
```

- Заполняются в истории, «переходе к дате» и поиске. В событиях и в ответе на отправку
  `status` — `null`, `isRead` — `false`: новое сообщение всегда `sent`.
- `isRead` раньше всегда был `false`.

**`ChatListItemDto`** — три новых поля, чтобы вести статусы без перезапроса истории:

```json
{ "lastReadSeq": 40,          // до какого seq я прочитал
  "outboxDeliveredSeq": 42,   // мои сообщения до этого seq доставлены (0 — ни одного)
  "outboxReadSeq": 41 }       // мои сообщения до этого seq прочитаны
```

Статус своего сообщения: `seq <= outboxReadSeq` — `read`, иначе `seq <= outboxDeliveredSeq` —
`delivered`, иначе `sent`. У `lastMessage` в списке чатов `status` и `isRead` заполнены.

**События** — только автору, чьё сообщение впервые получило статус, на все его соединения и в
журнал `/api/sync`:

```json
MessagesDelivered: { "chatId": "…", "userId": "<кто получил>", "seq": 42 }
MessagesRead:      { "chatId": "…", "userId": "<кто прочитал>", "seq": 41 }
```

Клиенту: `outboxDeliveredSeq = max(outboxDeliveredSeq, seq)` (для `MessagesRead` — оба поля),
затем пересчитать статусы своих сообщений чата. Значения только растут.

**Как устройству подтверждать доставку.** После применения событий из хаба или из
`GET /api/sync` — `POST /api/sync/ack { "pts": … }` с последним обработанным `pts`. Подтверждать
каждое событие не нужно: достаточно раз в несколько секунд или при сворачивании приложения.
Прочтение подразумевает доставку, поэтому клиент без ack (текущий веб-клиент) переводит
сообщения из `sent` сразу в `read`.

### 13.2. Прочтение на всех устройствах и «пометить непрочитанным»

**`ReadStateChanged(state)`** — на все устройства пользователя (и в журнал), когда на одном
из них сдвинулся указатель прочтения или изменилась метка «непрочитано»:

```json
{ "chatId": "…", "lastReadSeq": 41, "unreadCount": 1, "unreadMentionCount": 0, "markedUnread": false }
```

Клиенту: заменить эти поля в строке чата. Раньше другие устройства узнавали о прочтении
только после перезагрузки списка.

**`PUT /api/chats/{chatId}/marked-unread`** — поставить или снять метку «непрочитано»:

```json
{ "markedUnread": true }
```

- `204`. Метка видна только самому пользователю: `ChatListItemDto.markedUnread`; `unreadCount`
  она не меняет — клиент показывает точку или «1» сам.
- `POST /api/chats/{chatId}/read` снимает метку, даже если читать нечего.
- То же значение ещё раз — `204` без события.
- Ошибки: `403 NOT_A_MEMBER`, `429 RATE_LIMITED`.

### 13.3. Черновики

Один черновик на пользователя и чат, общий для всех его устройств.

**`PUT /api/chats/{chatId}/draft`** — сохранить:

```json
{ "text": "Буду в *12* ", "entities": [ … ], "replyToMessageId": "…" }   // всё, кроме text, необязательно
```

- `200` — `DraftDto` (ниже). Текст хранится **как набран**, без обрезки пробелов: курсор и
  пробел в конце не теряются. До 4096 символов.
- `entities` и `replyToMessageId` проверяются, как при отправке (смещения — по тексту как есть).
- Текст из одних пробелов без ответа — черновик удаляется: `204`.
- Тот же черновик ещё раз — `200` без события. Сохранять стоит с паузой в 1–2 секунды после
  остановки набора, а не на каждую клавишу: запрос входит в лимит команд.
- Ошибки: `400 MESSAGE_TOO_LONG`, `400 INVALID_ENTITIES`, `400 REPLY_TARGET_NOT_FOUND`,
  `403 NOT_A_MEMBER`, `429 RATE_LIMITED`.

**`DELETE /api/chats/{chatId}/draft`** — удалить. `204`; без черновика — `204` без события.

**Отправка сообщения в чат удаляет черновик** — с любого устройства, в том числе через хаб.
Пересылка черновик не трогает.

**`ChatListItemDto.draft`** — черновик или `null`; есть и в `GET /api/sync/state`, так что новое
устройство получает черновики сразу:

```json
"draft": { "text": "Буду в *12* ", "entities": [], "replyToMessageId": null,
           "updatedAt": "2026-09-30T10:15:00Z" }
```

**`DraftUpdated`** — на все устройства пользователя и в журнал:

```json
{ "chatId": "…", "draft": { … } }   // draft: null — удалён или отправлен
```

Клиенту: не перетирать поле ввода, в котором пользователь сейчас печатает, если
`updatedAt` пришедшего черновика не новее своего последнего сохранения.

## 14. План 2, Ф3: группы

Всё здесь — добавления. Тип чата `group` клиент уже знает; новые события текущий веб-клиент
не слушает.

### 14.1. Создание группы и системные сообщения

**`POST /api/chats/groups`**:

```json
{ "title": "Запуск", "memberIds": ["…", "…"] }   // memberIds может быть пустым
```

- `201` — `ChatListItemDto` создателя: `type: "group"`, `title`, `companion*` — `null`.
- Создатель — владелец (`owner`), остальные — участники (`member`). Себя и повторы в
  `memberIds` указывать можно — они не мешают.
- Не больше `Groups:MaxMembers` участников вместе с владельцем (по умолчанию 500).
- Участники получают **`ChatCreated`** со своей карточкой (у них одно непрочитанное —
  системное сообщение о создании). Другие устройства создателя узнают о группе через журнал
  `/api/sync`, как о созданном им личном чате.
- Системное сообщение о создании по хабу отдельно не приходит — его превью уже в карточке. В
  журнале `/api/sync` оно есть целиком, сразу после `ChatCreated` (с плана 2, Ф8; см. 19.2).
- Ошибки: `400 INVALID_TITLE` (после обрезки пробелов 1–128 символов), `400 TOO_MANY_MEMBERS`,
  `404 USER_NOT_FOUND` (кого-то нет или он деактивирован), `429 RATE_LIMITED`.

**`GET /api/chats/{chatId}`** — у участников новое поле `role`: `owner`, `admin` или `member`
(в личных чатах и «Избранном» все — `member`).

**Системные сообщения.** Что происходит в группе, записывается в историю сообщением
`type: "system"`:

```json
{
  "type": "system",
  "senderId": "<кто сделал>",
  "text": "Добавлены участники: Боб, Карл",       // то же словами, по-русски
  "action": {
    "type": "members_added",                        // group_created, title_changed, members_added,
                                                    // member_removed, member_left
    "userIds": ["…", "…"],                          // кого касается
    "title": null                                   // название — для group_created и title_changed
  }
}
```

- `action` — у системных сообщений, у остальных `null`. Клиенту лучше строить подпись из
  `action` (с актуальными именами и на языке интерфейса), а `text` показывать для незнакомого
  `action.type`. Текущий клиент покажет `text` как обычное сообщение от `senderId`.
- Системное сообщение нельзя править (`403 MESSAGE_NOT_EDITABLE`), отвечать на него
  (`400 REPLY_TARGET_NOT_FOUND`, и в черновике тоже), пересылать (`404 MESSAGE_NOT_FOUND`);
  поиск по сообщениям его не находит. Непрочитанным оно считается, как обычное.
- Сообщение о создании группы не приходит отдельным `MessageCreated`: оно уже есть в
  карточке `ChatCreated` как `lastMessage`.

### 14.2. Роли и права

Роли: `owner` (один на группу), `admin`, `member`. Права:

| Право | Что даёт | `member` по умолчанию | `admin` по умолчанию |
|---|---|---|---|
| `sendMessages` | писать и «печатает» | да | да |
| `sendMedia` | отправлять медиа (с Ф4) | да | да |
| `addMembers` | добавлять участников | да | да |
| `changeInfo` | менять название | нет | да |
| `removeMembers` | исключать участников и ограничивать их права | — | да |
| `deleteMessages` | удалять чужие сообщения у всех, в любое время | — | да |
| `addAdmins` | назначать админов | — | нет |

Владелец может всё. Итог для участника — права группы по умолчанию (`memberPermissions`),
поверх них его личные переопределения; для админа — набор админа, поверх него его
переопределения. Права админа (`removeMembers`, `deleteMessages`, `addAdmins`) участнику не
выдаются: для этого его назначают админом.

**`GET /api/chats/{chatId}`** — новые поля:

```json
{ "createdBy": "…",                 // создатель группы; null — не группа
  "myRole": "admin",
  "myPermissions": { … },            // что могу я; null — не группа
  "memberPermissions": { … } }       // права участников по умолчанию; null — не группа
```

**`GET /api/chats/{chatId}/members`** — участники группы: владелец, админы, затем участники
по времени вступления:

```json
[ { "userId": "…", "displayName": "Боб", "username": "bob", "role": "admin",
    "permissions": { "sendMessages": true, "sendMedia": true, "addMembers": true, "changeInfo": true,
                     "removeMembers": true, "deleteMessages": true, "addAdmins": false } } ]
```

**`PUT /api/chats/{chatId}/members/{userId}/role`** — `{ "role": "admin" }`:

- `admin` — назначить админом: владелец или админ с `addAdmins`.
- `member` — снять админа: только владелец.
- `owner` — передать группу: только владелец; сам он становится админом.
- Новая роль начинается без личных переопределений. `200` — `GroupMemberDto`.
- Ошибки: `400 NOT_A_GROUP`, `400 INVALID_ROLE`, `403 NOT_A_MEMBER`, `403 PERMISSION_DENIED`,
  `404 MEMBER_NOT_FOUND`, `429 RATE_LIMITED`.

**`PUT /api/chats/{chatId}/members/{userId}/permissions`** — личные переопределения, **целиком**:

```json
{ "sendMessages": false }     // указанное переопределяет, не указанное — как у роли; {} — снять всё
```

- Участника — владелец или админ с `removeMembers`, и только `sendMessages`, `sendMedia`,
  `addMembers`, `changeInfo`. Админа — только владелец, любые права. Владельца — никто.
- `200` — `GroupMemberDto` с итоговыми правами. То же ещё раз — без события.
- Ошибки: `400 NOT_A_GROUP`, `400 INVALID_PERMISSIONS` (право админа участнику),
  `403 NOT_A_MEMBER`, `403 PERMISSION_DENIED`, `404 MEMBER_NOT_FOUND`, `429 RATE_LIMITED`.

**`MemberUpdated`** — всем участникам, на все соединения и в журнал:

```json
{ "chatId": "…", "member": { GroupMemberDto } }   // при передаче группы — два события
```

**Что меняется для уже существующих команд в группе:**
- Отправка, пересылка в группу, правка и «печатает» без `sendMessages` —
  `403 PERMISSION_DENIED`. Чтение, реакции и прочтение — остаются.
- `DELETE …/messages/{messageId}?forEveryone=true` — участник с `deleteMessages` удаляет
  чужие сообщения в любое время; это попадает в журнал действий группы. Системные сообщения
  удаляет только он (их автор — нет).

### 14.3. Участники: добавление, исключение, выход

**`POST /api/chats/{chatId}/members`** — `{ "userIds": ["…"] }`:

- Нужно право `addMembers`. Уже состоящие пропускаются; `200` — массив `GroupMemberDto`
  добавленных (пустой — никого нового, событий нет).
- Новые участники видят всю историю, но непрочитанным считается только то, что после
  вступления. Они получают **`ChatCreated`** со своей карточкой (в ней системное сообщение
  «Добавлены участники: …» — одно непрочитанное).
- Прежние участники получают системное сообщение (`MessageCreated`, `ChatListUpdated`) и
  **`MemberAdded`**:

  ```json
  { "chatId": "…", "addedBy": "…", "members": [ GroupMemberDto, … ] }
  ```

- Ошибки: `400 NOT_A_GROUP`, `400 INVALID_REQUEST` (никого, кроме себя), `400 TOO_MANY_MEMBERS`,
  `403 NOT_A_MEMBER`, `403 PERMISSION_DENIED`, `404 USER_NOT_FOUND`, `429 RATE_LIMITED`.

**`DELETE /api/chats/{chatId}/members/{userId}`** — исключить; свой `userId` — **выйти**:

- Исключить: владелец — кого угодно, админ с `removeMembers` — только участников.
- Выйти может любой. Владелец при выходе передаёт группу самому давнему админу, а если
  админов нет — самому давнему участнику (им приходит `MemberUpdated`). Последний вышедший
  удаляет группу.
- Исключённый или вышедший теряет чат вместе с историей: `403 NOT_A_MEMBER` на всё, чата нет
  в списке. Его соединения перестают получать события чата, даже если чат был открыт
  (`JoinChat`); повторный `JoinChat` — ошибка.
- Все, включая исключённого, получают **`MemberRemoved`**:

  ```json
  { "chatId": "…", "userId": "<кого>", "removedBy": "<кто>" }   // removedBy: null — вышел сам
  ```

  Оставшимся приходит и системное сообщение (`member_removed` или `member_left`). У кого чат
  открыт (`JoinChat`), исключённому оно тоже приходит — это последнее событие группы для него.
- `204`. Ошибки: `400 NOT_A_GROUP`, `403 NOT_A_MEMBER`, `403 PERMISSION_DENIED`,
  `404 MEMBER_NOT_FOUND`, `429 RATE_LIMITED`.

Клиенту на `MemberRemoved` со своим `userId` — убрать чат из списка и закрыть, если открыт.

### 14.4. Изменение и удаление группы

**`PATCH /api/chats/{chatId}`** — меняются только указанные поля:

```json
{ "title": "Запуск v2",                              // нужно changeInfo
  "memberPermissions": { "sendMessages": false } }   // владелец или админ с removeMembers
```

- `title` — системное сообщение «Название группы изменено на …» всем участникам.
- `memberPermissions` — права участников по умолчанию; указанное меняется, остальное остаётся
  (`{ "sendMessages": false }` — группа только для чтения участникам). Только `sendMessages`,
  `sendMedia`, `addMembers`, `changeInfo`. Личные переопределения участников сильнее.
- `200` — `{ "chatId", "title", "memberPermissions" }` как сейчас; участникам то же приходит
  **`ChatUpdated`**. Без изменений — без события.
- Ошибки: `400 NOT_A_GROUP`, `400 INVALID_TITLE`, `400 INVALID_PERMISSIONS`, `403 NOT_A_MEMBER`,
  `403 PERMISSION_DENIED`, `429 RATE_LIMITED`.

Клиенту на `ChatUpdated`: обновить название в списке и шапке, пересчитать свои права
(`GET /api/chats/{chatId}` → `myPermissions`).

**`DELETE /api/chats/{chatId}`** — удалить группу у всех. Только владелец. `204`.
Все участники получают **`ChatDeleted`** `{ "chatId": "…" }`, их соединения перестают получать
события группы; история удаляется. Ошибки: `400 NOT_A_GROUP`, `403 NOT_A_MEMBER`,
`403 PERMISSION_DENIED`, `429 RATE_LIMITED`.

### 14.5. Журнал действий группы

**`GET /api/chats/{chatId}/audit?cursor=&limit=`** — для владельца и админов, новые первыми,
по умолчанию 50 записей (до 200):

```json
{
  "items": [
    { "id": 42, "action": "member_removed", "actorId": "…", "targetUserId": "…",
      "data": null, "createdAt": "2026-09-30T10:15:00Z" }
  ],
  "nextCursor": "41",     // передать как cursor за более старыми; null — всё
  "hasMore": true
}
```

| `action` | `targetUserId` | `data` |
|---|---|---|
| `group_created` | — | `{ title, memberIds }` |
| `title_changed` | — | `{ from, to }` |
| `member_permissions_changed` | — | `{ memberPermissions }` — переопределения по умолчанию |
| `members_added` | — | `{ userIds }` |
| `member_removed` | исключённый | — |
| `member_left` | вышедший | — |
| `role_changed` | участник | `{ role }` |
| `permissions_changed` | участник | `{ permissions }` — его переопределения |
| `ownership_transferred` | новый владелец | `{ reason: "owner_left" }` — если владелец вышел |
| `message_deleted` | автор сообщения | `{ messageId, seq }` — админ удалил чужое |

`actorId` — `null`, если аккаунта больше нет. Ошибки: `400 NOT_A_GROUP`, `400 INVALID_CURSOR`,
`403 NOT_A_MEMBER`, `403 PERMISSION_DENIED` (не админ).

### 14.6. Список чатов страницами

**`GET /api/chats/page?cursor=&limit=`** — те же `ChatListItemDto`, что `GET /api/chats`, по
50 (до 200) за раз:

```json
{ "items": [ ChatListItemDto, … ], "nextCursor": "AQ…", "hasMore": true }
```

- Порядок — по последней активности чата, новые первыми; при равенстве — по `chatId`.
  Страницы не пересекаются и не теряют чаты, пока ничего не меняется.
- Чат, получивший сообщение во время листания, уходит наверх: список после первой страницы
  стоит вести по событиям, а не перечитывать страницы.
- `GET /api/chats` без параметров работает, как раньше, — весь список.
- Ошибки: `400 INVALID_CURSOR`.

**`lastActivityAt` — время последней активности чата**, общее для всех участников: последнее
сообщение (в том числе системное) или создание чата. Раньше это было время последнего
сообщения, видимого самому пользователю. Отличие заметно в двух случаях: сообщение удалено у
всех или у себя — чат не опускается вниз (как в Telegram); `lastMessage` при этом по-прежнему
показывает последнее видимое сообщение.

## 15. План 2, Ф4: медиа

Всё здесь — добавления. Файлы хранятся в S3-совместимом хранилище (SeaweedFS в compose) и
никогда не идут через API: клиент загружает и скачивает их сам по коротким подписанным
ссылкам, которые выдаёт API. Сервер без хранилища (`Storage:Endpoint` не задан) отвечает на
ручки медиа `503 MEDIA_UNAVAILABLE`, остальное работает.

### 15.1. Загрузка и скачивание файлов

Загрузка — три шага:

1. **`POST /api/media/uploads`** — что будет загружено:

   ```json
   {
     "kind": "photo",              // photo, video, file, voice
     "fileName": "beach.jpg",      // только для показа; папки и управляющие символы отбрасываются
     "mimeType": "image/jpeg",     // пойдёт в Content-Type загрузки; только для показа
     "size": 734003,               // байты; проверяется до загрузки
     "width": 1280, "height": 720, // видео: размер кадра, как измерил клиент
     "durationMs": 5000,           // видео и голосовое; у голосового обязательно
     "waveform": [0, 12, 31],      // голосовое: до 256 значений 0–255
     "withThumbnail": true         // видео: клиент загрузит и кадр для превью
   }
   ```

   `201`:

   ```json
   {
     "attachmentId": "…",
     "uploadUrl": "https://chat.example.com/media/o/…?X-Amz-…",
     "contentType": "image/jpeg",
     "thumbnailUploadUrl": null,       // видео с withThumbnail: куда положить кадр
     "thumbnailContentType": null,     // image/jpeg — с ним загружать кадр (JPEG или PNG)
     "expiresAt": "2026-09-30T12:30:00Z"
   }
   ```

2. **`PUT {uploadUrl}`** — тело запроса — файл, заголовок `Content-Type` — ровно
   `contentType` из ответа (другой хранилище отвергнет: он входит в подпись). Токен API не нужен.
3. **`POST /api/media/uploads/{attachmentId}/complete`** → `200 AttachmentDto`. Сервер читает
   загруженное: настоящий размер, SHA-256, тип по содержимому. Фото должно быть JPEG, PNG, GIF
   или WebP — сервер измеряет его (с учётом поворота камеры) и делает превью до 640 px по
   длинной стороне; видео — MP4, MOV или WebM, голосовое — Ogg, WebM, MP4 или MP3. Не прошедший
   проверку файл удаляется. Повтор вызова возвращает тот же файл.

```json
// AttachmentDto
{
  "id": "…",
  "kind": "photo",
  "fileName": "beach.jpg",
  "mimeType": "image/png",      // что сервер нашёл в файле, а не что заявил клиент
  "size": 734003,
  "width": 1600, "height": 900, // фото — как показывать; видео — со слов клиента
  "durationMs": null,
  "waveform": null,
  "hasThumbnail": true,         // есть превью: фото; видео, если клиент прислал кадр
  "state": "stored"             // expired — оригинал удалён политикой хранения, осталось превью
}
```

Лимиты — настройки инстанса: файл до `Media:MaxFileSizeMb` (100 МБ), фото до
`Media:MaxPhotoSizeMb` (20 МБ) и 50 Мпикс, не больше `Media:MaxPendingUploads` (50)
незавершённых загрузок на пользователя. Ссылка на загрузку живёт `Media:UploadUrlMinutes`
(30 мин); загрузка, не завершённая за `Media:PendingUploadHours` (24 ч), удаляется.

**Скачивание.** **`POST /api/media/links`** `{ "attachmentIds": ["…"] }` (до 100) →

```json
{ "items": [ { "attachmentId": "…", "url": "https://…", "thumbnailUrl": "https://…", "expiresAt": "…" } ] }
```

- Файлы, которые пользователю не видны, в ответ не попадают. Видны свои файлы и файлы из
  сообщений чатов, где пользователь сейчас состоит (15.2).
- Ссылки подписаны и живут `Media:DownloadUrlMinutes` (60 мин); `url` — `null` у истёкшего
  файла, `thumbnailUrl` — `null`, если превью нет.
- Фото, видео и голосовые отдаются для показа (`inline`) с типом, найденным сервером; прочие
  файлы — только как скачивание: `application/octet-stream`, `Content-Disposition: attachment`
  с именем файла. На проде Caddy добавляет к файлам `X-Content-Type-Options: nosniff` и
  `Content-Security-Policy: sandbox` — загруженный HTML или SVG не исполнится на сайте (R32).
- **`GET /api/media/{attachmentId}?thumbnail=true`** — `302` на ту же ссылку, для кода,
  который скачивает с токеном. Для `<img>` — ссылки из `POST /api/media/links`: браузер не
  отправит токен с запросом картинки. Ошибка: `404 ATTACHMENT_NOT_FOUND`.

На проде хранилище отдаётся с того же адреса, что и сайт (`/media/…`), — CSP сайта не
меняется. Если хранилище на другом адресе (локальная разработка), сервер добавляет его в
`img-src`, `media-src` и `connect-src`.

### 15.2. Сообщения с файлами и альбомы

**`POST /api/chats/{chatId}/messages`** — новое поле `attachmentIds`:

```json
{ "text": "С моря", "attachmentIds": ["…", "…"], "clientMessageId": "…" }
```

- До 10 файлов — альбом, в указанном порядке. Фото и видео — вместе; файлы — только с
  файлами; голосовое — одно. Иначе `400 INVALID_ALBUM` (и при повторах в списке).
- Файл — завершённая загрузка отправителя или файл, который он видит в своих чатах: переслать
  чужое фото можно, не скачивая и не загружая заново. Иначе (чужой, незавершённый, удалённый)
  — `404 ATTACHMENT_NOT_FOUND`.
- Текст — подпись, может быть пустым или отсутствовать; разметка и упоминания — как у текста.
- В группе нужно право `sendMedia` (и `sendMessages`) — иначе `403 PERMISSION_DENIED`.

**`MessageDto`** — `type: "media"` и новое поле `attachments` — `AttachmentDto[]` (15.1) в
порядке альбома; у остальных сообщений — пустой массив. Так же в `lastMessage` списка чатов,
в `MessageCreated` и в журнале `/api/sync`.

- **Пересылка** сообщения с файлами переносит их по ссылке — новые загрузки не нужны, участники
  целевого чата получают к ним доступ. В группе без права `sendMedia` пересылка файлов —
  `403 PERMISSION_DENIED`.
- **Правка** меняет подпись; у сообщения с файлами её можно стереть (`text: ""`). Файлы правкой
  не меняются.
- **Удаление у всех** убирает файлы из сообщения: участники чата теряют к ним доступ (если не
  видят их в другом сообщении); у загрузившего файл остаётся.
- На сообщение с файлами можно ответить; в `replyTo.text` — подпись.
- Текущий веб-клиент покажет сообщение с файлами как текст подписи (без подписи — пустым).

### 15.3. Медиа-галерея чата

**`GET /api/chats/{chatId}/media?filter=&cursor=&limit=`** — сообщения чата с файлами нужного
вида или со ссылками, **новые первыми** (как их показывает галерея), по 50 (до 100):

| `filter` | Что попадает |
|---|---|
| `media` | сообщения с фото или видео |
| `files` | с файлами |
| `voice` | с голосовыми |
| `links` | с адресом `http(s)://` в тексте или со ссылкой (`link`) в разметке |

- Ответ — `{ items: MessageDto[], nextCursor, hasMore }`, те же `MessageDto`, что в истории, с
  `attachments`; превью — через `POST /api/media/links`. Альбом — одно сообщение с несколькими
  файлами.
- Удалённое у всех и скрытое у себя не попадает. Правка, добавившая ссылку, добавляет
  сообщение во вкладку `links`.
- Ошибки: `400 INVALID_FILTER` (нет или неизвестный `filter`), `400 INVALID_CURSOR`,
  `403 NOT_A_MEMBER`.

### 15.4. Аватары пользователей и групп

Аватар — фото из загрузок пользователя (15.1): сначала загрузить `kind: "photo"`, потом
назначить. Картинку клиент берёт по `avatarId` через `POST /api/media/links` (`thumbnailUrl` —
превью до 640 px, для списков его хватает).

- **`PUT /api/users/me/avatar`** `{ "attachmentId": "…" }`, **`DELETE /api/users/me/avatar`** →
  `200` — свой профиль (`GET /api/users/me`). Свои устройства и все, с кем есть общий чат,
  получают **`UserUpdated`** `{ userId, displayName, username, avatarId }` (и в журнал
  `/api/sync`). Аватар пользователя видят все вошедшие.
- **`PUT /api/chats/{chatId}/avatar`**, **`DELETE /api/chats/{chatId}/avatar`** → `200` —
  `ChatUpdatedDto`. Только группа (`400 NOT_A_GROUP`), нужно право `changeInfo`
  (`403 PERMISSION_DENIED`). Участники получают системное сообщение (`photo_changed` /
  `photo_removed`, «Фото группы изменено» / «Фото группы удалено») и `ChatUpdated`; запись в
  журнале действий. Фото группы видят её участники.
- Повтор того же фото — без событий и сообщений.
- Ошибки назначения: `400 INVALID_AVATAR` (не фото), `404 ATTACHMENT_NOT_FOUND` (не своя
  завершённая загрузка — выбрать чужое фото из чата нельзя).

Новое поле **`avatarId`** (`null` — нет аватара): `GET /api/users/me`, `GET /api/users/{id}`,
поиск пользователей, участники в `GET /api/chats/{chatId}` и `GET .../members`, сам
`ChatDetailDto` и `ChatListItemDto` (для группы — её фото, для личного чата — фото собеседника),
`ChatUpdated`.


### 15.5. Сколько хранятся файлы

- Файл, на который ничего не ссылается (не отправлен, сообщения с ним удалены у всех, не
  аватар), удаляется через `Media:UnusedFileHours` (24 ч) — пропадает и у загрузившего.
- Политика хранения инстанса (D2): `Media:RetentionDays` — оригиналы старше удаляются, превью
  остаются, у файла `state: "expired"`, в ссылках `url: null`. По умолчанию выключена (0).
  Аватары не истекают. Истёкший файл нельзя отправить заново (`404 ATTACHMENT_NOT_FOUND`);
  сообщения с ним остаются, пересылка переносит его как есть.

## 16. План 2, Ф5: приватность и профиль

### 16.1. Настройки приватности и присутствие

**`GET /api/users/me/privacy`**, **`PUT /api/users/me/privacy`**:

```json
{ "lastSeen": "everybody", "messages": "contacts", "groupAdd": "nobody" }
```

- Значения — `everybody`, `contacts` (те, с кем есть общий чат: списка контактов в продукте
  нет) или `nobody`; по умолчанию всё `everybody`. В `PUT` меняются только переданные поля,
  ответ — все настройки. Свои устройства получают **`PrivacyUpdated`** (и в журнал `/api/sync`).
- `lastSeen` — кто видит online и время последнего визита. Правило взаимное, как в Telegram:
  скрывший своё (`nobody`) не видит чужое. Для присутствия `everybody` и `contacts` одно и то же —
  его и так видят только собеседники. Смена действует сразу: собеседники получают
  `UserOnlineChanged(false)` (или `true` при открытии), скрывший — то же о них.
- `messages` и `groupAdd` — 16.2.
- Ошибки: `400 INVALID_PRIVACY`.

**Статус пользователя** (`GET /api/users/{id}/status`, `POST /api/users/status`) — новое поле
`lastSeenAt`: когда пользователь был в сети последний раз, если он сейчас не в сети и показывает
это вызывающему. Собеседник, который скрыл присутствие (или которого не видно из-за своей
настройки), — `isOnline: false`, `lastSeenAt: null`; раньше такого случая не было. Не
собеседник — по-прежнему `404` (одиночный запрос) или пропуск (пакетный).

`GET /api/users/status` (кто из собеседников в сети) и `UserOnlineChanged` учитывают те же
правила.

### 16.2. Кто пишет в личку и кто добавляет в группы

- **`POST /api/chats/private/{userId}`** создаёт новый чат, только если это разрешает настройка
  `messages` собеседника: `everybody`; `contacts` — если у двоих уже есть общий чат (группа);
  `nobody` — никому. Иначе `403 PRIVACY_RESTRICTED`. Уже существующий личный чат открывается и
  работает при любой настройке.
- **Добавление в группу** — при создании (`POST /api/chats/groups`) и позже
  (`POST /api/chats/{chatId}/members`) — по настройке `groupAdd` каждого добавляемого, с тем же
  смыслом `contacts` (общий чат с добавляющим). Если кого-то добавить нельзя, не добавляется
  никто: `403 PRIVACY_RESTRICTED`, в ответе — **`userIds`**, кого именно:

  ```json
  { "errorCode": "PRIVACY_RESTRICTED", "userIds": ["…"], "detail": "These users do not allow you to add them to groups" }
  ```

  Клиент может убрать их и повторить.

### 16.3. Блокировки

- **`PUT /api/users/{userId}/block`**, **`DELETE /api/users/{userId}/block`** → `204`; повтор — не
  ошибка. **`GET /api/users/me/blocked`** — заблокированные, последние первыми (как
  `GET /api/users/{id}`). Свои устройства получают **`BlockListChanged`** `{ userId, blocked }`.
- В личном чате никто из двоих не пишет, не ставит реакции и «печатает»: заблокировавшему —
  `403 USER_BLOCKED` (разблокировать, чтобы писать), заблокированному — `403 PRIVACY_RESTRICTED`,
  как при настройках приватности: о блокировке ему не сообщается. Историю оба читают.
- Заблокированный не создаёт личный чат с заблокировавшим и не добавляет его в группы
  (`403 PRIVACY_RESTRICTED`), не видит его online и last seen (для него тот «не в сети» без
  времени, `UserOnlineChanged(false)` приходит сразу) и аватар: `avatarId: null` в профиле,
  поиске, списке чатов, участниках, а ссылку на файл не получить. `UserUpdated` ему не приходит.
- Ошибки: `400 INVALID_REQUEST` (себя), `404 USER_NOT_FOUND`.

### 16.4. Имя и пароль

- **`PATCH /api/users/me`** `{ "displayName": "Алиса" }` → `200` — свой профиль. Имя — 1–100
  символов после обрезки пробелов (`400 INVALID_DISPLAY_NAME`). Свои устройства и собеседники
  получают `UserUpdated` (16.3: кроме заблокированных). В сообщения имя не копируется — история
  и списки показывают новое имя.
- **`POST /api/auth/password`** `{ "currentPassword": "…", "newPassword": "…" }` → `204`. Новый
  пароль — как при регистрации (от 6 символов, до 72 байт в UTF-8). Все остальные входы
  пользователя заканчиваются сразу: их refresh-токены больше не работают, соединения с хабом
  закрываются; это устройство остаётся в системе. Уже выданные им access-токены живут до
  истечения (минуты). Лимит — как у входа, 5 попыток в минуту с IP.
  Ошибки: `400 WRONG_PASSWORD` (не `401`: клиент не должен принять его за истёкший токен),
  `400 PASSWORD_TOO_LONG`, `400 VALIDATION_ERROR`, `429 RATE_LIMITED`.

## 17. План 2, Ф6: организация чатов и поиск

### 17.1. Закрепление, архив, mute

Новые поля **`ChatListItemDto`**: `pinnedPosition` (1 — самый верхний; `null` — не закреплён),
`archived`, `isMuted`, `mutedUntil` (`null` — не заглушён или заглушён навсегда).

- **`PUT /api/chats/{chatId}/pinned`** `{ "pinned": true }` → `200 { "chatIds": [...] }` —
  закреплённые, сверху вниз. Новый закреп — наверх; не больше 10 (`400 TOO_MANY_PINNED`);
  закрепление достаёт чат из архива.
- **`PUT /api/chats/pinned`** `{ "chatIds": [...] }` — новый порядок, ровно те же чаты
  (`400 INVALID_REQUEST`).
- **`PUT /api/chats/{chatId}/archived`** `{ "archived": true }` → `200 ChatStateDto`
  `{ chatId, archived, isMuted, mutedUntil }`. Архивный чат открепляется. Новое сообщение
  (не своё) возвращает чат из архива, если он не заглушён.
- **`PUT /api/chats/{chatId}/muted`** `{ "muted": true, "until": "…" }` — до момента; без
  `until` — навсегда; `{ "muted": false }` — снять → `200 ChatStateDto`. Заглушённый чат не
  присылает уведомлений (push — Ф7) и не выходит из архива; счётчик непрочитанных работает.
  `until` в прошлом — `400 INVALID_REQUEST`.
- Свои устройства получают **`PinnedChatsChanged`** `{ chatIds }` и **`ChatStateChanged`**
  (`ChatStateDto`) — и при возвращении из архива новым сообщением.
- Ошибки всех: `403 NOT_A_MEMBER`.

**Список чатов.** `GET /api/chats` (весь список, в том числе в `/api/sync/state`) — закреплённые
сверху, в своём порядке; архивные — в списке, с `archived: true`, чтобы клиент без поддержки
архива их не потерял. **`GET /api/chats/page`** — основной список: первая страница начинается
со всех закреплённых (не больше 10, они не входят в `limit`), дальше — по активности, без
закреплённых и без архивных. **`GET /api/chats/page?archived=true`** — архив.

### 17.2. Папки

```json
// FolderDto
{
  "id": "…",
  "title": "Работа",
  "includePrivate": false,     // все личные чаты вне архива
  "includeGroups": true,       // все группы вне архива
  "onlyUnread": false,         // только с непрочитанным (или с меткой «непрочитано»)
  "chatIds": ["…"],            // перечисленные явно — даже из архива
  "pinnedChatIds": ["…"]       // закреплённые в папке, сверху вниз; они тоже в папке
}
```

- **`GET /api/folders`** — папки пользователя в его порядке.
- **`POST /api/folders`** (`FolderDto` без `id`) → `201`; новая — последней.
- **`PATCH /api/folders/{folderId}`** — только переданные поля; списки заменяются целиком.
- **`DELETE /api/folders/{folderId}`** → `204`; чаты остаются где были.
- **`PUT /api/folders/order`** `{ "folderIds": [...] }` — ровно все папки в новом порядке.
- **`GET /api/folders/{folderId}/chats?cursor=&limit=`** — чаты папки теми же `ChatListItemDto`:
  первая страница начинается с закреплённых в папке (вне `limit`), дальше — по активности.
- Лимиты: 20 папок, 200 перечисленных и 10 закреплённых чатов в папке; название 1–64 символа.
  В папку можно положить только свои чаты.
- Свои устройства получают **`FoldersChanged`** `{ folders: FolderDto[] }` — все папки после
  любого изменения.
- Ошибки: `400 INVALID_TITLE`, `400 TOO_MANY_FOLDERS`, `400 INVALID_REQUEST`, `400 INVALID_CURSOR`,
  `404 FOLDER_NOT_FOUND`.

### 17.3. Глобальный поиск

**`GET /api/search/messages?q=&chatId=&senderId=&from=&to=&type=&cursor=&limit=`** — поиск по
сообщениям всех чатов, где пользователь состоит сейчас; тот же полнотекстовый поиск, что в чате
(русская морфология, слова как префиксы). Удалённые, скрытые у себя и системные сообщения не
находятся; вышел из группы — её сообщения пропадают из поиска.

```json
{
  "items": [
    {
      "message": MessageDto,
      "chat": { "chatId": "…", "type": "group", "title": "Команда", "companionId": null,
                "companionName": null, "avatarId": null }
    }
  ],
  "nextCursor": "AQ…", "hasMore": true, "query": "запуск"
}
```

- Новые первыми (по времени), по 20 (до 100).
- Фильтры: `chatId`, `senderId`, `from`/`to` (время, `to` не включается), `type` — `text` или
  `media` (ищется подпись).
- В `message` не заполнены `status` и `isRead` — их даёт история чата.
- Ошибки: `400 INVALID_QUERY` (короче 2 символов), `400 INVALID_FILTER`, `400 INVALID_CURSOR`,
  `403 NOT_A_MEMBER` (`chatId` чужого чата).

## 18. План 2, Ф7: устройства и push

### 18.1. Устройства

Устройство — это один вход (логин или регистрация) со всеми обновлениями токена после него;
его id — `sid` в access-токене. Устройство пропадает после logout, когда истекает его
refresh-токен или когда его выводят из системы с другого устройства.

**`GET /api/devices`** — открытые входы, последние активные первыми:

```json
{
  "items": [
    { "id": "…", "isCurrent": true, "signedInAt": "2026-09-30T10:00:00Z",
      "lastActiveAt": "2026-09-30T12:40:00Z", "userAgent": "Mozilla/5.0 …", "pushEnabled": true }
  ]
}
```

- `lastActiveAt` — последнее обновление токена: открытый клиент делает его каждые несколько минут.
- `userAgent` — как клиент представился при последнем обновлении токена.
- `pushEnabled` — устройство подписано на push (18.2).

**`DELETE /api/devices/{deviceId}`** → `204` — выход на этом устройстве: его refresh-токен
перестаёт работать, соединения с хабом закрываются сразу; уже выданный access-токен живёт до
истечения (минуты). Можно и текущее — то же, что logout. Ошибки: `404 DEVICE_NOT_FOUND` (чужое
или уже вышло).

### 18.2. Подписка на push

WebPush (VAPID): сервер шлёт уведомления через push-сервис браузера, а браузер показывает их
service worker'ом, даже когда вкладка закрыта.

**`GET /api/push/config`** → `{ "enabled": true, "vapidPublicKey": "BN…" }`. `enabled: false` —
на сервере push выключен (не настроены ключи), предлагать его не нужно. `vapidPublicKey` —
`applicationServerKey` для `pushManager.subscribe`.

**`PUT /api/push/subscription`** → `204`. Тело — `PushSubscription.toJSON()` браузера:

```json
{ "endpoint": "https://fcm.googleapis.com/fcm/send/…", "expirationTime": null,
  "keys": { "p256dh": "BN…", "auth": "…" } }
```

- Подписка принадлежит устройству (входу, от которого запрос); новая заменяет старую.
- Подписку, которую тот же браузер отдал другому входу (например, до выхода и входа другим
  пользователем), сервер переносит на этот вход: уведомления прежнего сюда больше не придут.
- Logout, logout-all, смена пароля и выход на устройстве удаляют подписку вместе с устройством.
- Принимаются только адреса известных push-сервисов по https: Google (Chrome), Mozilla
  (Firefox), Microsoft (Edge), Apple (Safari); список — настройка `Push:AllowedHosts`.
- Ошибки: `400 INVALID_SUBSCRIPTION` (адрес не push-сервиса, ключи не того вида),
  `404 DEVICE_NOT_FOUND` (вход уже закончился), `503 PUSH_UNAVAILABLE`.

**`DELETE /api/push/subscription`** → `204` — больше не слать на это устройство; без подписки —
тоже `204`.

### 18.3. Уведомления о новых сообщениях

О каждом новом сообщении сервер шлёт push на подписанные устройства участников чата, кроме:

- отправителя (все его устройства);
- тех, у кого сейчас открыто соединение с хабом: они получают сообщение через `MessageCreated`;
- заглушивших чат (`muted`; счётчик непрочитанных при этом работает);
- заблокировавших отправителя (в группе; в личке он и так не напишет);
- устройств, вход которых закончился.

Браузер расшифровывает уведомление и отдаёт его service worker'у в событии `push`;
`event.data.json()`:

```json
{
  "kind": "message",
  "chatId": "…", "chatType": "group", "chatTitle": "Команда",
  "messageId": "…", "seq": 42,
  "senderId": "…", "senderName": "Алиса",
  "messageType": "media", "text": "подпись…", "attachmentKind": "photo", "attachmentCount": 3,
  "createdAt": "2026-09-30T12:40:00Z"
}
```

- `kind` — пока только `message`; неизвестный пропускать.
- `chatTitle` — только у группы; в личном чате показывать `senderName`.
- `text` — начало текста (100 символов, как в `ChatListUpdated`); у медиа — подписи, может быть
  пустым: тогда показывать вид файла (`attachmentKind`) и их число.
- `messageType: "system"` — событие группы (добавили, переименовали); `text` описывает его словами.
- В service worker нет access-токена: всё для показа — в самом уведомлении. По нажатию —
  открыть чат `chatId`; историю клиент догрузит сам.
- Уведомления одного чата, ещё не доставленные на устройство (оно офлайн), push-сервис
  схлопывает: доходит последнее (`Topic` — id чата). Недоставленное хранится сутки
  (`Push:TtlSeconds`).
- Push — не гарантия доставки: очередь на отправку в памяти сервера, при его перезапуске
  неотправленные уведомления теряются. Сами сообщения — в журнале `/api/sync`.
- Подписку, которую push-сервис больше не знает (`404`/`410`), сервер удаляет.

## 19. План 2, Ф8: полная история на новом устройстве

Новое устройство получает то же, что видно на старом (D3): снимок `GET /api/sync/state`, историю
каждого чата страницами назад до первого сообщения (`GET /api/chats/{id}/messages/cursor`) и
файлы по ссылкам (`POST /api/media/links`), пока они хранятся на сервере. Дальше — журнал
`GET /api/sync` от `pts` снимка. Это проверяет сквозной тест: устройство, которое было с самого
начала и вело состояние по журналу, и устройство, вошедшее после всех действий плана, видят одно и
то же — чаты, сообщения, правки, удаления, реакции, статусы, прочтение, черновики, закрепы,
архив, mute, папки, приватность, блокировки, профиль.

### 19.1. Снимок — всё состояние пользователя

**`GET /api/sync/state`** — новые поля (добавления):

```json
{
  "pts": 128,
  "chats": [ /* ChatListItemDto — все, и архив: закрепы, mute, черновики, счётчики */ ],
  "folders": [ /* FolderDto, как GET /api/folders */ ],
  "privacy": { "lastSeen": "everybody", "messages": "contacts", "groupAdd": "everybody" },
  "blockedUserIds": ["…"],
  "me": { "userId": "…", "username": "alice", "email": "…", "displayName": "Алиса", "avatarId": null }
}
```

- Всё в одном снимке базы с `pts`: изменение либо уже в снимке, либо придёт в `/api/sync` после
  него — ни потерь, ни двойного применения.
- `blockedUserIds` — только id, как в `BlockListChanged`; профили — `GET /api/users/me/blocked`.
- `me` — как `GET /api/users/me`; дальше его меняет `UserUpdated` со своим `userId`.

### 19.2. Журнал несёт сообщения целиком

- `lastMessage` в карточке чата (`ChatCreated`, список чатов) — превью: без разметки, реакций,
  ответа, пересылки и `action`. Историю строить по `MessageCreated` и страницам истории, не по
  карточке.
- Сообщение о создании группы теперь есть в журнале участников как `MessageCreated` (после
  `ChatCreated`); раньше его знала только карточка, и устройство, которое ведёт историю по
  журналу, теряло `action` и разметку. Живьём по хабу оно по-прежнему не приходит.

## 20. План 4: контракт для генерации клиентов

### 20.1. OpenAPI: nullable-поля и события хаба

Формат запросов и ответов не изменился — изменилось только описание
(`/swagger/v1/swagger.json`), из которого веб-клиент генерирует свои типы.

- **Nullable — как в коде.** Раньше описание помечало `nullable` все строки и массивы, а
  вложенные объекты (`lastMessage`, `draft`, `replyTo`, …) — нет. Теперь `null` разрешён ровно
  там, где сервер может его прислать: `text`, `senderName`, `type`, массивы `entities`,
  `reactions`, `attachments` — всегда значение; `lastMessage`, `draft`, `replyTo`,
  `forwardFrom`, `action`, `myPermissions` — объект или `null` (`allOf` + `nullable: true`).
- **Схемы событий хаба.** В `components.schemas` появились полезные нагрузки событий, которые
  не встречаются в REST: `MessageDeletedDto`, `ReceiptDto`, `ReadStateDto`, `DraftUpdatedDto`,
  `MembersAddedDto`, `MemberRemovedDto`, `MemberUpdatedDto`, `ChatDeletedDto`,
  `UserUpdatedDto`, `BlockListChangedDto`, `FoldersDto`. Какое событие что несёт — в разделах
  12–19 выше; те же объекты приходят в `payload` записей `GET /api/sync`.
- Все поля ответа присутствуют в JSON всегда (в том числе со значением `null`), кроме
  помеченных `x-omitted-when-null: true` — их при `null` в JSON нет: `url`, `userId` и `language`
  у сущностей разметки, поля `PermissionsPatchDto` и необязательные поля ProblemDetails.
  `required` в описании по-прежнему не указывается.

### 20.2. `GET /api/config` (новая)

Лимиты и переключатели экземпляра — чтобы клиент проверял ввод до отправки, а не узнавал о
лимите из ошибки. Читать один раз после входа. Нужен вход.

```json
{
  "messages": { "maxLength": 4096, "maxAttachments": 10,
                "reactions": ["👍", "❤️", "😂", "😮", "😢", "🙏", "👎", "🔥", "🎉"],
                "editWindowHours": 48, "deleteWindowHours": 48 },
  "media":    { "enabled": true, "maxFileSize": 104857600, "maxPhotoSize": 20971520, "retentionDays": 0 },
  "groups":   { "maxMembers": 500, "maxTitleLength": 128 },
  "push":     { "enabled": false }
}
```

- `reactions` — набор `Messages:Reactions` в порядке показа; другие реакции сервер не примет.
  Исправлено попутно: набор из настроек, короче стандартного, раньше молча дополнялся
  стандартными реакциями (список из `appsettings.json` склеивался с заданным).
- `editWindowHours` / `deleteWindowHours` — сколько часов автор может править и удалять у всех;
  `0` — без срока.
- `media.enabled: false` — хранилище не настроено, ручки медиа отвечают `503 MEDIA_UNAVAILABLE`.
  Размеры — в байтах; `maxPhotoSize` — для файлов с `kind: photo`.
- `push.enabled` — то же, что в `GET /api/push/config`; ключ для подписки — там.

### 20.3. История вокруг сообщения и вперёд (новые)

Раньше историю можно было листать только назад от свежих сообщений (`…/messages/cursor`) или
от даты (`…/messages/at`). Открыть чат на найденном сообщении или на оригинале ответа и
листать оттуда вниз было нечем.

**`GET /api/chats/{chatId}/messages/{messageId}/context?limit=30`** — окно вокруг сообщения:
половина `limit` до него, само сообщение, остальное после. **`GET
/api/chats/{chatId}/messages/after?seq={seq}&limit=30`** — сообщения новее `seq`.

```json
// MessageWindowDto
{
  "items": [ /* MessageDto, от старых к новым */ ],
  "nextCursor": "…",   // к странице до первого — в …/messages/cursor?cursor=
  "hasMore": true,     // есть сообщения старше первого
  "hasNewer": true     // есть новее последнего — …/messages/after?seq={seq последнего}
}
```

- Видимость — как в истории: удалённые у всех и скрытые у себя не приходят.
- `limit` — 1…100. Ошибки: `403 NOT_A_MEMBER`; для `context` — `404 MESSAGE_NOT_FOUND` (не
  этот чат, удалено у всех или у себя).

### 20.4. CSP: `blob:` для картинок и видео

Заголовок `Content-Security-Policy` разрешает `blob:` в `img-src` и `media-src` (только там):
веб-клиент показывает превью выбранных файлов и измеряет видео до загрузки по адресам
`blob:`, которые создаёт сама страница. Скрипты и запросы (`script-src`, `connect-src`) — как
были, `'self'`.

### 20.5. Service worker веб-клиента: `worker-src` и кеш `sw.js`

- В заголовке `Content-Security-Policy` явно указан `worker-src 'self'`: push-уведомления
  веб-клиента обрабатывает service worker (`/client/sw.js`). Раньше то же разрешалось неявно —
  через `script-src 'self'`; чужие воркеры по-прежнему запрещены.
- `/client/sw.js` отдаётся с `Cache-Control: no-cache`, как `index.html`: имя у воркера постоянное,
  и из кеша браузер держал бы старую версию. Файлы из `/client/assets/` — как были, навсегда.

## 21. Сквозные проверки клиента: лимиты и разбор запроса

### 21.1. «Печатает» и черновики — свой лимит

`POST /api/chats/{chatId}/typing`, `PUT` и `DELETE /api/chats/{chatId}/draft` больше не
расходуют лимит команд (отправка, правка, реакции и прочее — 20 за 10 секунд на пользователя),
у них свой такой же (`RateLimiting:ComposerPer10Seconds`, 20 за 10 секунд). Раньше каждое
сообщение быстрой переписки стоило трёх команд («печатает», отправка, «перестал») и уже
седьмое подряд упиралось в `429`. Ответы и коды прежние.

### 21.2. Слишком большой или оборванный запрос

Запрос, который Kestrel не смог прочитать, раньше превращался в `500 INTERNAL_ERROR`, а через
Caddy — в `502`. Теперь:

- тело больше лимита ручки (64 КБ у отправки, правки и черновика) — `413 REQUEST_TOO_LARGE`;
- тело, оборванное клиентом, — `400 BAD_REQUEST`.

Caddy не пропускает к API тела больше 1 МБ (`413`). На тело во много раз больше лимита
соединение может оборваться раньше ответа, и тогда клиент увидит `502` — такие запросы от
настоящего клиента не приходят.

## 22. План 5: исправления по ревью клиента

### 22.1. `POST /api/auth/logout` завершает вход, с которого пришёл запрос

Раньше выход отзывал только сессию переданного `refreshToken`. Клиент с истёкшим access-токеном
получал `401`, обновлял пару и повторял выход с прежним, уже заменённым токеном — и сервер не
отзывал ничего: вход оставался живым, устройство — в списке, соединения хаба — открытыми.
Теперь выход завершает и вход (`sid`) access-токена запроса. `refreshToken` в теле по-прежнему
принимается; ответ и коды прежние.

| `USER_BLOCKED` | 403 | Личный чат: пользователь сам заблокировал собеседника — разблокировать, чтобы писать |
| `PERMISSION_DENIED` | 403 | Группа: у пользователя нет нужного права или роли (в `detail` — какого) |
| `ACCESS_DENIED` | 403 | Прочие отказы в доступе |
| `USER_NOT_FOUND` | 404 | Пользователь не найден (или вне общих чатов — для статуса) |
| `CHAT_NOT_FOUND` | 404 | Чат не найден |
| `FOLDER_NOT_FOUND` | 404 | Папки: нет такой папки у пользователя |
| `DEVICE_NOT_FOUND` | 404 | `DELETE /api/devices/{id}`: не устройство пользователя или на нём уже вышли; подписка на push: вход запроса уже закончился |
| `MEMBER_NOT_FOUND` | 404 | Группа: пользователь не её участник |
| `UPLOAD_NOT_FOUND` | 404 | Завершение загрузки: нет такой незавершённой загрузки пользователя (или она удалена как неудачная или устаревшая) |
| `ATTACHMENT_NOT_FOUND` | 404 | `GET /api/media/{id}`: файла нет, он не виден пользователю или (оригинал) истёк; отправка: файл не завершён, не виден отправителю или истёк |
| `MESSAGE_NOT_FOUND` | 404 | `read`, правка, удаление: сообщения нет в этом чате (для правки — или оно удалено); пересылка: сообщение не видно пользователю |
| `USERNAME_TAKEN` | 409 | Регистрация: логин занят (без учёта регистра) |
| `EMAIL_TAKEN` | 409 | Регистрация: email занят (без учёта регистра) |
| `USER_ALREADY_EXISTS` | 409 | Регистрация: гонка двух одинаковых регистраций |
| `CLIENT_MESSAGE_ID_CONFLICT` | 409 | Отправка: `clientMessageId` уже занят сообщением в другом чате |
| `TOO_MANY_UPLOADS` | 409 | Загрузка: у пользователя уже `Media:MaxPendingUploads` незавершённых загрузок |
| `RATE_LIMITED` | 429 | Превышен лимит; `Retry-After` — через сколько секунд повторить (в хабе — 20 вызовов за 10 с на соединение) |
| `REQUEST_TOO_LARGE` | 413 | Тело запроса больше лимита ручки (64 КБ у отправки, правки и черновика) или 1 МБ на прокси |
| `INTERNAL_ERROR` | 500 | Ошибка сервера; `traceId` — для поиска в логах |
| `MEDIA_UNAVAILABLE` | 503 | Ручки медиа на сервере без файлового хранилища |
| `PUSH_UNAVAILABLE` | 503 | Подписка на push на сервере без VAPID-ключей |
